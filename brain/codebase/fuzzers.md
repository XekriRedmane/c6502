# The C++ fuzzers and how they were checked

- The fuzzers are cpp/src/fuzz/ and `c6502cpp fuzz` since G6 of step 9 (27 Nov 2026). The generators draw from py_random in the order the Python generators drew, so every seed is the program Python wrote for it: 9,000 programs matched on the first build, and golden/fuzz/ checks seeds 0 to 99 in a doctest case.
- Porting a generator byte for byte comes down to Python's order of evaluation. A list literal's elements are evaluated before the `choice` that takes it, so `r.choice([("assign", ("var", r.choice(locals).name), c), ...])` draws the inner choice first. An f-string's fields go left to right, `a or r.random() < p` draws only when `a` is false, and a helper such as `lvalues()` that calls `index()` draws on every call, even when its result is filtered away. Reading each draw site with those rules in mind was enough; no trace of the draws was needed.
- The runner names each error by the Python class cpp_backend.py would have raised (an `InternalError` is `AssertionError`, py65's word read at $FFFF is `IndexError: bytearray index out of range`), so its lines and the reducer's signatures read as the Python runner's did. The comparison of 1,000 seeds' verdicts and results matched with no difference.
- `-j` starts a process per seed, because the IR checks' switch, the TAC optimizer's observer, and the caches in ir_check.cpp and fnmatch.cpp are process globals. Making them `thread_local` would let seeds run on threads. 300 stmts programs take 39 s in one process and 8 s with `-j 12`.
- YARPGen's programs depend on the standard library it was built with, since it draws through `std::uniform_int_distribution`, `std::discrete_distribution`, and `std::shuffle`. An MSVC build wrote other programs on all of seeds 1 to 100, so fuzz/build_yarpgen.sh builds with Zig's clang (libc++), which it downloads. func.c's first lines hold the build date and the command line, so a comparison of two builds drops them.
- A reducer is compared by breaking a pass in the working tree only (G6 made the TAC constant fold of a subtraction add 1), finding seeds it makes fail, and reducing each with both reducers on that build. Revert with `git checkout <file>` and rebuild before committing anything.
- A comparison script that imports the Python modules about to be deleted stops working as soon as their dependencies are edited. In G6, cpp_backend.py had already lost `enable_ir_check` when one more reduction was compared, and fuzz/runner.py failed at import. Keep the Python side's edits for the commit that deletes it, after the last comparison, or run the comparison from the commit before.
