# The games' machines in C++ and their checks

- cpp/src/sim/apple2.h (Zork), lode_runner.h, ali_baba.h, and disk2.h (G5 of step 9, 27 Nov 2026) are sim/apple2.py, lode_runner.py, ali_baba.py, and disk2.py. cpp/src/sim/games.h holds the scripts and the setups the Python tests played them in, and `c6502cpp game-run GAME SCRIPT [--exe PATH]` plays one and writes its events. The doctest cases are cpp/tests/test_zork_interpreter_sim.cpp, test_lode_runner_sim.cpp, test_ali_baba_sim.cpp, and test_disk2.cpp, gated on the game variables with `doctest::skip(bool)` at registration, so a run without the files reports them as skipped rather than passed. All 22 take about 22 seconds.
- The machines run their own loops over `Cpu::step` and decode each instruction's soft-switch access before it runs, as the Python ones did. The CPU's read and write callbacks would also see `JMP ($C0xx)` and the opcode fetch, which the Python decoding leaves out, and `Cpu::run` has no stop check between an instruction and the next cycle check, where the Python machines check their `stop`. Every comparison passed on the first build with that design.
- The Python machines' lockstep mode is sim/lockstep.py's `MachineRecorder`: the loop calls `before` and `after` around each instruction, and anything the machine changes between them (a hook, a soft switch's value stored in memory, a delay loop taken in one step) starts a new segment, which `cpu-run` runs for exactly the segment's count (the `instructions` field). Ali Baba's helper hooks had captured the memory object at setup, which the recorder swaps for a recording copy, so a hook must read `machine.mpu.memory` when it runs.
- tools/compare_game_machines.py writes the same text as `game-run` from the Python machines, by standing in for `MachineRecorder` (to count instructions and take steps) and wrapping `_record` (or Zork's `calls` list) for the state digests. It stays with sim/'s machines until R. The originals run first, since a C program runs until it has made the original's number of events.
- The examples' linker scripts place sections by object file name (`decode.o(.text ...)` in interpreter.ld), so a build that names its objects `zork-decode.o` links a different program, which in G5 made 8 more calls than the original. Build each example's objects in a directory of their own, named after their units.
- No script of the three games executes an undefined opcode, on the original or on the C program.
