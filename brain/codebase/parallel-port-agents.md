# Porting tests with agents in parallel worktrees

- G1 of step 9 (26 Nov 2026) ported 495 Python tests to doctest with five agents at once, each in a worktree of its own (`isolation: "worktree"`), after the lead had committed the shared library and one ported module as the model. Each agent took about an hour, and together they ran in about 90 minutes, where one agent would have taken five hours or more.
- A worktree that `isolation` makes starts at main, not at the lead's branch. The agents were told to move to the lead's commit first. `git reset --hard <hash>` was refused by the permission classifier for one of them, and `git merge --ff-only <hash>` reached the same state, since the lead's commit descends from main.
- The brief was one file (C:/w/g1/brief.md) that every agent read, with a batch file listing each agent's modules and their tests, and a short prompt per agent with that batch's special cases. The agents were forbidden to edit the shared library, and each put its helpers in its own files, so the lead could merge them with `git cherry-pick <base>..<branch>` per agent. Over 95 commits, one conflict came up, in a module docstring that two batches edited.
- Each agent made a full build of its own worktree (about 9 minutes) and then incremental ones, all through tools/run_exclusive.sh. The five builds and test runs queued on the lock, and a lead's build waited up to 12 minutes for it.
- In G4 of step 9 (27 Nov 2026) the batch-2 helper forked itself into five forks that shared its worktree and build directory. Each fork wrote only its own cpp/tests files and built and ran its cases through run_exclusive.sh, and the helper did the deletions and the commits. The 277 tests were ported in about 30 minutes, and every case passed. One fork's build compiled every fork's files, so an error in any file would have stopped the link for all of them. The forks' stop hook made each commit its reflect notes, five commits with overlapping bullets, which the helper folded into one. The group's lead then said that its rule caps the helpers at two, which forks break, so a helper does its batch itself unless the lead allows more agents. A fork can't call SubagentHandback, which returns "not active for this agent", so its report is its final plain text.
- Agents ran the reflect skill on their own, before their reports, and committed notes to brain/ in their branches, which merged cleanly.
- A brief for a helper names every limit the lead works under, the cap on agents included. G4's test brief listed the build lock, line endings, and commits but not "spawn no agents or forks", and the batch-2 helper forked five times before a message reached it. In G4 two helpers of about 278 tests each took about 55 minutes, and the lead's harness and its own 118 tests were done before they started, so the batches only had to port tests.
- `git commit -- <paths>` commits each named file as it stands on disk, so in a worktree that several agents share it takes in whatever another agent has just written to the same file. In G4, fork B's reflect commit ce0a2253 took in two bullets that another fork had added to brain/codebase/long-runs-and-scratch-scripts.md, one of them the same lesson as fork B's. Agents that share a worktree write their notes to files of their own, or leave every commit to the helper that leads them.
- `git commit -- <paths>` refuses a path that git doesn't track yet ("pathspec did not match any file(s) known to git"). A helper whose brief forbids `git add` can delete files but can't commit a new one, so a brief that expects new files says how they are added, such as `git add -N -- <paths>` of those paths alone. In group R of step 9 the lead made such a helper's blocked commit itself, with the helper's message file, while the helper waited for leave to run `git add -N`. When leave arrives, run `git log --oneline -1 -- <paths>` before committing, since the paths may already be in a commit.
