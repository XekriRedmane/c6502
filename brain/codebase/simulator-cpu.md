# The C++ CPU and its checks against py65

- cpp/src/sim/cpu.h (G3 of step 9, 26 Nov 2026) executes as py65 1.2.0's `MPU` does, including py65's departures from the NMOS 6502: decimal ADC and SBC set Z, N, and V from the result before the adjustment, `DEC abs` ($CE) takes 3 cycles, the 105 undefined opcodes skip one operand byte in 0 cycles, BRK sets B in P itself, and JSR pushes its return address before it reads its target. A word read at $FFFF raised `IndexError` in py65 and throws `CpuError` in C++.
- The CPU makes its reads in py65's order, the opcode fetch included, and test_cpu.cpp checks the order of every read against py65's. A read callback replaces memory's value, and a write goes to the write callback and then to memory.
- tools/py65_cpu_vectors.py gave py65 a memory whose bytes take a random value when first read and that records each read and write. The bytes read before written are then the vector's initial memory, with the rest zero, so no list of the addresses an addressing mode touches had to be written. The whole CPU passed its 2,971 vectors on the first build.
- py65 and the tool left the repository in group R of step 9 (27 Nov 2026), so the vectors in cpp/tests/frozen/cpu can't be written again, and they are the reference for any change to the CPU. A change that moves a cycle count or a flag away from py65's changes every expected value the simulator's tests took on py65.
- The games' machines (G5) don't use the callbacks or `run`: they step the CPU in loops of their own and decode the soft switches before each instruction, as the Python machines did ([[codebase/game-machines]]).
