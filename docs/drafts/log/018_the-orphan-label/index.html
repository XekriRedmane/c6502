Compiler log · #018

The orphan label

A two-line peephole, 84 broken tests, and a codegen convention I didn't know I was leaning on.

Project c6502 Target Apple II beam state machine Result 6 bytes / 23 cycles saved Lesson within-iteration invariants matter

The residue

I was reading the optimized output of a freshly-compiled Apple II routine — beam_target_tick, the state machine that drives a player-tracking beam — when I tripped over this:

LDX   beam_snd_ctr
TXA
BMI   .if_end@0
TXA
BPL   .sx_done@1
.sx_done@1:
TXA
SEC
SBC   #$01
STA   beam_snd_ctr

Three things look wrong. The first TXA sets flags for BMI — that's expected. The second TXA sets flags that the next instruction (BPL) reads, fine in isolation. But the branch goes to .sx_done@1, which is the immediately-following label. Both arms (taken and fall-through) reach the same instruction — the branch is a pure no-op. And after we arrive at .sx_done@1, a third TXA sets A to X's value, which A was already equal to from the previous two TXAs.

Three useless instructions in a row. The simulator says the program is correct; the assembler is happy; the diff against the gold .asm file passes because the gold .asm has the same residue. But six bytes and a handful of cycles are sitting there doing nothing on every call.

Where it came from

The label name is the clue. .sx_done@1 — sign-extension done. The C source was doing this:

int8_t snd_ctr = (int8_t)beam_snd_ctr;
if (snd_ctr >= 0) {
    uint8_t pitch = beam_jingle[snd_ctr];
    beam_snd_ctr = (uint8_t)(snd_ctr - 1);
    snd_delay_up(pitch, 0x0A);
}

C99 §6.3.1.1.2 says any int8_t at an arithmetic operand position promotes to int — a 2-byte signed type on this compiler. The >= 0 comparison, the array index, and the snd_ctr - 1 subtraction all happen at int width. So the TAC lowering sign-extends the byte to two bytes before any of those operations.

The sign-extension lowering in tac_to_asm._translate_sign_extend emits this diamond:

LDA   src.high          ; copy of src byte; sets N
BMI   sx_neg
LDA   #$00              ; high byte = 0 for non-negative
JMP   sx_done
sx_neg:
LDA   #$FF              ; high byte = 0xFF for negative
sx_done:
STA   dst.high

That's the textbook 6502 sign-extension. But every use of the widened value in this routine only touches the low byte: the bit-7 test (one byte's worth of sign), the indexed lookup (an 11-byte table, low byte is enough), the subtract followed by truncation back to uint8_t (high byte of result is dead). The byte-granular DCE in the asm-SSA pipeline notices dst.high has no readers and drops the STA. With the store gone, both LDA #$00 and LDA #$FF have nothing to do, and dead_a_arith reaps them too. branch_invert sees BMI sx_neg; JMP sx_done; sx_neg: and rewrites it to BPL sx_done. dead_label_drop removes the now-orphan sx_neg.

What's left, after all those passes, is the skeleton of a diamond with both arms gone and the label of the join point still in place:

LDA   src.high
BPL   sx_done
sx_done:

The body of beam_target_tick then needs the low byte of the widened value for the indexed load and the subtract, which is held in X (because direct_index_load fused a LDA; TAX into LDX earlier). So we get a few TXAs for various flag-setting and arithmetic-staging purposes, and the diamond skeleton sits in the middle, three useless bytes wide.

The BPL to next instruction is unreachable as a state change. So is at least one of the bracketing TXAs. Nothing in the existing pass pipeline catches either.

Two peepholes

The two cleanups are independent and both straightforward.

1. Drop Branch(_, L); Label(L)

If a conditional branch's target is the immediately following label, both arms reach the same instruction. The branch reads flags but writes nothing — no register, no memory, no flag, no PC change relative to fall-through. Drop it. About thirty lines of code, including the linear walk and the test class.

2. Drop redundant register-to-register Movs

The existing redundant_load_elimination tracks which memory operand each of A, X, Y currently mirrors. If LDA M is about to load A and A already mirrors M, drop the load (gated on flag-deadness — the load also sets N/Z, and if downstream code reads those, we can't elide).

That same machinery covers register-to-register transfers naturally. After LDX M, X's mirror list contains M. After a following TXA, A's mirror list also contains M. A second TXA, no intervening writes — A and X both still mirror M, both still hold M's value. The transfer is a no-op for the value; if flags are dead too (or the Z-reflects tracker already covers the operand the transfer would set Z from), drop it.

Six new lines in _is_redundant_load and _flags_redundant_at, plus seven test cases covering the various preserves/drops. The existing 30 tests stayed green.

Wire them in, recompile beam_target_tick, look at the output. Clean:

LDX   beam_snd_ctr
TXA
BMI   .if_end@0
SEC
SBC   #$01
STA   beam_snd_ctr

Six bytes saved on this hot path. Run the full test suite to make sure nothing else broke.

Ship it, break 84 tests

Ran 2739 tests in 82.493s

FAILED (failures=84, skipped=26)

The failures spanned the chapter test corpus — chapter_7/nested_if, chapter_8/while, chapter_8/for_decl, chapter_9/stack_arguments, basically any program with a loop and a comparison. Whatever broke, it broke broadly.

First step: bisect. The two peepholes are independent. Stash one, retry.

$ git stash push passes/redundant_load.py tests/test_redundant_load.py
$ uv run python -m unittest tests.test_inc_peephole.TestIncPeepholeCorrectness.test_byte_overflow_propagates_to_high_byte
AssertionError: 0 != 300

The reg-to-reg pass is innocent. branch_to_next_drop alone breaks loops. So the question is: what does dropping a no-op branch have to do with a 16-bit-counter loop terminating immediately?

The failing program is the simplest possible motivator:

long sum300(void) {
    long s = 0;
    for (int i = 0; i < 300; i++) s += 1;
    return s;
}

The loop should iterate 300 times. The optimized output runs zero iterations. Look at it:

.loop@0_start:
   SEC
   BPL   .loop@0_break
   INC   __local_sum300__s_0
   ...

That's the loop header. The comparison sequence — LDA i_0; SEC; SBC #$2C; LDA i_1; SBC #$01 — is gone. There's nothing computing i < 300. The BPL reads whatever N was left over from the prologue's last instruction (an LDA #$00), which means N=0, branch taken, loop exits before the body runs.

The new pass dropped one BVC. How did that turn into deleting an entire 16-bit comparison?

Tracing a fixedpoint

The asm-peephole loop runs a sequence of 30-odd passes in order until a full sweep produces no changes. With 84 tests failing, the question is which pass in which iteration drops the comparison chain. So I instrumented the loop — print the instruction count, the Sub count, and the LDA-into-A count after every pass, every iteration, for the failing function.

--- iter 0 ---
  after asm_dead_store:   total=44 sub=2 lda-into-A=6
  after dead_a_arith:     total=43 sub=2 lda-into-A=6     ; 1 dropped
  after dead_label_drop:  total=38 sub=2 lda-into-A=6     ; orphan labels reaped
  after branch_invert:    total=38 sub=2 lda-into-A=6
  after branch_to_next_drop: total=37 sub=2 lda-into-A=6     ; BVC + Label dropped
--- iter 1 ---
  after asm_dead_store:   total=37 sub=2 lda-into-A=6
  after dead_a_arith:     total=33 sub=0 lda-into-A=4     ; 4 dropped — SBC chain gone

Iteration 0 is mine: branch_to_next_drop drops one branch. Iteration 1, before anything else gets a chance: dead_a_arith takes out four instructions. Both Subs (the SBC #$2C and the SBC #$01) and two of the LDAs. The entire 16-bit comparison.

So dead_a_arith believed those instructions' effects were dead. Look at what the IR looks like going into it:

  6: Label .loop@0_start
  7: LDA i_0 → A
  8: SEC
  9: SUB Imm(44) → A          ; SBC #$2C — writes A, N, Z, C, V
 10: LDA i_1 → A
 11: SUB Imm(1) → A           ; SBC #$01 — writes A, N, Z, C, V
 12: Label .jcmp_novf@0
 13: Branch PL → .loop@0_break  ; reads N

There's the smoking gun. .jcmp_novf@0. The label that the original BVC targeted is still sitting there at position 12 — orphaned (the only thing referencing it was the BVC I just dropped) but not yet reaped, because dead_label_drop ran before branch_to_next_drop in the iteration's pass order.

And dead_a_arith, walking forward from the SBC #$01 at position 11, looking to decide whether to drop it, asks all_flags_dead_at(12): "are flags dead starting at position 12?"

The flag-dead convention

Here's what all_flags_dead_at does, paraphrased:

while idx < len(instrs):
    if isinstance(instrs[idx], Branch):     return False
    if isinstance(instrs[idx], (Add, Sub)): return False  ; reads C
    if isinstance(instrs[idx], (Jump, Ret, Return, Label)): return True
    if _overwrites_all_flags(instrs[idx]):  return True
    idx += 1

The forward walk treats any Label as a safe terminator — "flags are dead from here onward, drop the writer." The docstring justifies this on a codegen invariant:

"The N/Z status of subsequent paths is each block's responsibility; if the next block's first instruction is a Branch, the soundness of declaring flags dead here depends on c6502's emission convention always setting N/Z before any Branch the lowering needs to read — which it does."

That invariant is true at tac_to_asm emit time. Every block that ends in a Branch has its own flag-setter inside it; the analysis can rely on that and skip the cross-block walk. It's an honest performance optimization — the alternative is a real CFG dataflow on flag liveness, which costs more.

But the invariant is brittle, and I just broke it. My pass dropped the BVC. The orphan Label(.jcmp_novf@0) remained, immediately followed by BPL .loop@0_break. The "block" beginning at that label has exactly one instruction in it — the BPL — and that instruction is a Branch that reads flags it didn't itself set. The walk hits the Label, returns "flags dead," and dead_a_arith drops the SBC.

One pass later, dead_label_drop would have reaped .jcmp_novf@0 (no remaining references). Two iterations later, the structure would look right. But within iteration 1, the orphan label is enough to lie to all_flags_dead_at, and the damage compounds: drop SBC #$01, then in the next inner pass of dead_a_arith the LDA i_1 becomes A-dead too, then SBC #$2C, then LDA i_0. By the end of one outer iteration, the whole comparison is gone.

Drop the label, save the chain

The fix is one extra clause in the new pass: when dropping Branch(_, L); Label(L), also drop the Label(L) if no other Branch / Jump / Phi-arg references it. Pre-scan the function once, count refs, and use the count to decide.

def _rewrite_function(fn):
    ref_counts = _label_ref_counts(fn.instructions)
    out = []
    i = 0
    while i < len(fn.instructions):
        a = fn.instructions[i]
        if (isinstance(a, asm_ast.Branch)
                and i + 1 < len(fn.instructions)
                and isinstance(fn.instructions[i + 1], asm_ast.Label)
                and a.target == fn.instructions[i + 1].name):
            # The Branch owns one reference. If that's the only one,
            # the Label is orphan after we drop the Branch — drop
            # both in the same sweep, so flags_dead_at doesn't see
            # a fall-through-only Label between a flag-setter and
            # the next-block's Branch within this iteration.
            label_name = fn.instructions[i + 1].name
            if ref_counts.get(label_name, 0) <= 1:
                i += 2     ; drop both
            else:
                i += 1     ; drop only the branch
            continue
        out.append(a)
        i += 1
    return asm_ast.Function(..., instructions=out)

That's it. Same-iteration label cleanup closes the window. dead_a_arith in iteration 1 now sees SBC #$01; BPL .loop@0_break directly — no intervening label — and all_flags_dead_at walks past the SBC, hits the Branch, returns False. The SBC stays. The whole chain stays. The loop terminates.

Full suite: Ran 2740 tests in 79s. OK.

On beam_target_tick itself, the original target: 810 → 804 bytes, 3516 → 3493 whole-program cycles, 427 → 404 function cycles.

What it taught

Two things in tension.

The first is mundane: peephole passes don't compose freely with each other inside a fixedpoint loop. Each pass has a contract over what IR shapes it produces and consumes. When pass A produces a shape that pass B in the same iteration interprets differently, you can get one-iteration-window bugs that look like the world ending. The pass order matters; the within-iteration transient states matter.

The second is more specific to this codebase: convention-based fast paths in analyses leave debt for new peepholes to repay. The Label-as-flag-terminator rule in all_flags_dead_at is correct given the codegen invariant, and the alternative (true CFG dataflow) would cost real compile time. So the analysis takes the shortcut, the codegen agrees to maintain the invariant, and every peephole author thereafter inherits the obligation to either honor the invariant or be loud about breaking it.

My pass broke it by accident — not because the analysis was wrong, and not because my rewrite was wrong, but because there's a transient state inside one fixedpoint iteration where neither contract holds. That's the kind of thing the test corpus catches and a unit test for the pass in isolation will not catch. It's also the kind of thing you find only when you walk the per-pass IR snapshot through the fixedpoint by hand, watching counts change.

The fix isn't to make all_flags_dead_at conservative at Labels — that would slow down a workhorse analysis to defend against future bad citizens. The fix is to make the new pass a good citizen: maintain the invariant by reaping the orphan label in the same sweep, so the analysis never sees a violated state.

I've added the rule to project memory. The next pass that drops a control-flow instruction will start from "if this could leave an orphan label adjacent to a Branch, drop the label too." Future me will probably still re-discover it once.
