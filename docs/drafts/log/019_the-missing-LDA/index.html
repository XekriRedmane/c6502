Compiler log · #019

The missing LDA

Three call sites silently lost their argument, the sim test agreed it was fine, and the bug had been there as long as reg("A") had.

Project c6502 Target Apple II beam state machine Bug class A-liveness across reg-attr Calls Result three calls now pass their pitch

A pitch arg, vanished

I was reading the optimized output of beam_target_tick.c — the state machine that drives a player-tracking beam on an Apple II — and an instruction I expected to see wasn't there. Two of the three calls into the click-helper trampolines looked like this:

CLC
ADC   #$02
STA   beam_y
LDX   #$0A
JMP   snd_delay_down

The C source calls snd_delay_down(0x10, 0x0A) — pitch is $10, clicks is $0A. The LDX #$0A at the bottom carries the clicks argument; the JMP tail-calls into the helper. But where's the LDA #$10 for the pitch? It's never set up. The A register at the point of the JMP holds beam_y + 2 — the side effect of the ADC; STA three lines earlier.

The third call, the jingle tick, was worse:

LDX   beam_snd_ctr
TXA
BMI   .if_end@0
SEC
SBC   #$01
STA   beam_snd_ctr
LDX   #$0A
JSR   snd_delay_up

The C source asks for snd_delay_up(beam_jingle[snd_ctr], 0x0A). There's no LDA beam_jingle,X anywhere. The A register at the JSR holds the decremented counter — neither the jingle byte the call wanted nor anything meaningful as a pitch.

Three calls. Three missing LDAs. And the test suite, which includes a per-example sim differential that re-runs each example under unoptimized and optimized pipelines and asserts they produce identical observable state, was perfectly happy.

A register IS a calling convention

The example declares its externs with c6502's reg(...) attribute:

extern void snd_delay_up(
    uint8_t pitch __attribute__((reg("A"))),
    uint8_t clicks __attribute__((reg("X"))));

The annotation pins each parameter to a 6502 register at the calling-convention boundary. The caller writes pitch directly into A and clicks into X before the JSR. The callee reads its parameters straight out of those registers — no zero-page slot, no soft-stack push, just the registers. For one-byte arguments to leaf helpers, it's the cheapest calling convention the machine offers.

This is how snd_delay_up / snd_delay_down were declared, and the @zp-link-meta block at the top of the .asm confirmed it:

; ext snd_delay_down params=__zpabi_snd_delay_down__pitch,__zpabi_snd_delay_down__clicks param_regs=A,X
; ext snd_delay_up   params=__zpabi_snd_delay_up__pitch,__zpabi_snd_delay_up__clicks   param_regs=A,X

So the compiler knew. The link metadata, written by passes/zp_link_metadata.py, faithfully recorded that the callees take A and X as arg registers. The lowering pass tac_to_asm emitted the right shape too — I checked. The Mov-into-A was present in the asm IR immediately after the SSA round-trip:

Mov(Imm(10), Reg(A))     ; LDA #10 — clicks, staged through A for TAX
Mov(Reg(A), Reg(X))     ; TAX     — clicks now in X
Mov(Imm(16), Reg(A))     ; LDA #$10 — pitch
Call(name='snd_delay_down', reg_args=[])

The Mov(Imm(16), Reg(A)) was there at IR level. Something after that point dropped it.

Bisecting the peepholes

c6502's asm-level peephole fixedpoint runs around thirty passes per iteration. I wrote a small bisection script: build the IR up to the point where the peephole loop starts, then run each pass in order, asserting after each that the offending atom — Mov(Imm(16), Reg(A)) — was still present.

after split_mem_to_mem: present
after inc_peephole:     present
after dec_peephole:     present
... (eleven more passes)
after asm_dead_store:   present
after dead_a_arith:     dropped!

The killer was apply_dead_a_arith_elimination, the pass that drops instructions whose only observable side effects are writes to A and the flags, when A and the flags are dead afterward. Its eligibility check is a single predicate: is A dead at the instruction right after this one?.

The kills_a contract

dead_a_arith asks asm_liveness.a_dead_at(instrs, after). That function walks the CFG forward from the position. At each instruction it asks two binary questions:

  • reads_a? — does this instruction read A's current value? If yes, A is live; return False.
  • kills_a? — does this instruction write A without reading it first? If yes, A's prior value is dead from this point; terminate this CFG path safely.

The order matters. reads_a is checked first; if it fires, we don't even ask about the kill. The same instruction can be a read-then-kill — ALU ops like ADC #imm read A as the accumulator and write A as the result, and they're correctly modeled as a read.

A Call instruction — a 6502 JSR — was modeled like this:

def reads_a(instr):
    ...
    return False              # Call is not a read

def kills_a(instr):
    ...
    if isinstance(instr, asm_ast.Call):
        return True            # Callees clobber A
    return False

The "callees clobber A" half is fine. A JSR may land in a function that uses A as scratch, then return with whatever 1-byte value it wants to leave in A as a return slot. Without knowing what the callee does, the conservative move is to say "treat A as redefined after this JSR" — i.e., the JSR is a kill.

The "Call is not a read" half is where the model fell apart. For most callees, that's right too — under the default zp_abi calling convention, the caller writes parameters into ZP slot bytes before the JSR; the callee reads them from those slots, not from A. The JSR doesn't observe A's contents at the moment of transfer.

But for a callee declared with reg("A") on a parameter, the JSR does observe A's contents. The compiler arranged for A to hold the argument just before the JSR; the callee depends on that. Treating Call as kill-without-read drops the very LDA the calling convention was set up to demand.

Diagnosis

The model "Call kills A, never reads A" was a global statement that quietly stopped being true the moment c6502 grew a register-passing calling convention. The same code that had been correct for years became incorrect — silently — when reg("A") shipped.

Two atoms, one field

The fix needs the liveness model to know which registers each call site reads as incoming arguments. That information already exists — tac_to_asm has the callee's ZpLayout.param_registers in hand when it emits the Call atom. It just needed to travel with the atom into the asm IR.

I added a reg_args field to the asm IR's Call node — a list of register names ("A", "X", "Y") naming the registers the callee reads as parameters:

-- before
| Call(identifier name)

-- after
| Call(identifier name, string* reg_args)

And taught tac_to_asm to populate it. At the direct-call site, after walking the callee's per-byte param_registers list and emitting the per-byte Mov-into-register sequence, it collects the register names that were used and threads them onto the Call:

seen: set[str] = set()
for r in layout.param_registers:
    if r and r not in seen:
        seen.add(r)
        reg_args.append(r)
...
emitted.append(asm_ast.Call(name=name, reg_args=reg_args))

The liveness predicate consults it. reads_a(Call) now returns True iff "A" is in the Call's reg_args. kills_a still returns True for every Call — that part was always right, and read-then-kill ordering means reads_a wins.

I built the test program, ran compile.py, looked at the output. The LDA #$0A — the clicks-staging that gets folded to LDX #$0A — was still there. The Mov(Imm(16), Reg(A)) was still gone.

The tail-call rewrite, again

The peephole loop runs to a fixed point. Each pass is a candidate rewriter; the loop iterates until a full sweep produces no change. Pass interactions can be subtle: one pass enables another, two passes might interfere, and a bug that looks like it lives in pass A might actually live in pass B's effect on A's input.

I extended the bisection one more pass at a time. The fix held through the entire fixedpoint. The Mov(Imm(16), Reg(A)) survived all the way to the last iteration. Then I looked at what happened between fixedpoint iterations and found it.

There's a peephole called apply_tail_call that rewrites the pattern Call(name); Return(_) at the end of a function into Jump(target=name) — a JMP instead of JSR+RTS, saving a byte and a stack push/pop pair. It's the optimization that turns "call snd_delay_down, then return" into "jump straight to snd_delay_down and let its RTS unwind both layers".

The rewrite was dropping the reg_args. The Jump atom didn't carry the field at all. So on the iteration after tail_call fired, the liveness walker saw a Jump to an extern target — no in-function label index — and its handling of Jump was the same as for any intra-function goto: follow the target if local, otherwise terminate the CFG path silently. A's load looked dead again. Round two of dead_a_arith dropped it.

Same fix, second atom: add reg_args to Jump, propagate it in tail_call, consult it in the liveness walker:

if isinstance(instr, asm_ast.Jump):
    if "A" in instr.reg_args:
        return False              # tail-call reads A
    tgt = label_to_index.get(instr.target)
    if tgt is not None:
        stack.append(tgt)
    return True

The check is on reg_args, not on "is the target an in-function label". Long-branch trampolines target in-function .skip labels too, and their reg_args is empty — those keep working the way they always did. The distinction is intrinsic to the atom, not derived from naming.

Rebuilt, ran the example, and the LDA was finally there:

CLC
ADC   #$02
STA   beam_y
LDX   #$0A
LDA   #$10
JMP   snd_delay_down

Why the test let it through

The example has a sim differential test — tests/test_beam_target_tick_sim.py. It inlines the example source, adds a main() driver that exercises each branch of the dispatch under known inputs, records observable state to a flat byte array, and asserts three things: the unoptimized output matches a hand-computed expected, the optimized output matches the same expected, and unopt and opt produce identical bytes.

The test was passing. With the bug. For a while.

The inline source defined its own stubs for the click helpers, with bodies that recorded the arguments they received into observable state. But the stubs were declared like this:

void snd_delay_up(uint8_t pitch, uint8_t clicks) {
    snd_up_calls = (uint8_t)(snd_up_calls + 1);
    snd_up_last_pitch = pitch;
    snd_up_last_clicks = clicks;
}

Plain parameters. No reg(...) attribute. The example's actual extern declaration uses reg-attr; the test program's inline definitions don't. Inside the test's single-TU compilation, snd_delay_up resolved to the local definition — and the local definition's calling convention was the default zp_abi-with-slots, not reg-passing.

The bug only triggers when the call goes through the reg-passing path. The test exercised the slot-passing path. Same surface program, fundamentally different ABI under the hood. The differential test was correctly proving that the slot-passing pipeline was self-consistent — which it was — and was structurally incapable of catching a bug in a calling convention it wasn't using.

The fix to the test was a five-line change: copy the extern declaration's attributes onto the inline definitions. With reg-attr on both sides, the test compiled the same program shape as the real example. With the optimizer fix removed, the test failed loudly: pitch $19 vs expected $19, then pitch $09 on the next scenario where expected was $19 — every snd_up_last_pitch field was off by however much the residual A register happened to be after the previous control flow.

Lesson

A sim differential test is only as good as the ABI of its inline stubs. If the example uses an attribute-controlled calling convention, the test stubs need to mirror those attributes — otherwise the test exercises a different program than the example does, and is structurally blind to bugs in the example's ABI path.

The local copies

Central asm-liveness predicates aren't the only place where "is A dead?" gets asked. A handful of peepholes that need the predicate maintain their own local copies — usually because they wanted slight variations on the eligibility (different kinds of "kill", different CFG-walk semantics) when the central version didn't quite fit. The local copies were written before reg_args existed; they all had the same bug, latent until exercised.

  • redundant_load_after_rmw.py — local _reads_a and _kills_a mirror the central pair. Patched both to consult reg_args.
  • dec_register_peephole.py — has a more aggressive local _a_dead_at that follows unconditional Jumps. Patched to recognize a tail-call Jump (reads_a via reg_args) as not dead.

None of these fired on the example I was working with — the example's shape didn't trigger them — but every pass that scans for A-liveness near a Call now needs the same insight. Better to patch them all together than to discover the next missing LDA from a different angle.

What it taught

Three things, ordered loosely from most concrete to most general:

An asm atom is a structural carrier for ABI information, not just an opcode. Adding reg_args to Call (and to Jump, via the tail-call rewrite) wasn't just a fix for one liveness predicate — it makes the calling convention's reads visible to every pass that walks the IR. Future passes that ask "what does this Call observe?" can answer it locally instead of having to recover the information by joining against a sibling table.

Compiler invariants quietly stop being true. "A Call kills A and never reads A" was a valid statement of c6502's semantics for most of the project's life — until the day reg("A") shipped and made it false at every reg-attr call site. There was no compile error to catch the moment of invalidation. Nothing in the type system flagged it. The condition was implicit, encoded in three or four predicate functions, and it broke silently the day the precondition no longer held universally.

Tests have ABIs too. The sim differential test was the right idea — same surface program, run through both pipelines, assert identical observable state. But the test program's ABI mattered. The example's externs had attributes the test's inline stubs didn't, so the test compiled a related-but-different program, and the differential said "the related program passes through both pipelines unchanged" — which was true, and not the question being asked.

The next time I'm adding a sim differential for an example that uses any ABI-affecting attribute — reg, zp_abi, whatever lands next — the first thing I'll do is copy the extern declarations verbatim into the inline stubs. If the test passes too easily, that's the first place to look.
