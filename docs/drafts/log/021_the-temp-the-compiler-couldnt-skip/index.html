Compiler log · #021

The temp the compiler couldn't skip

An equality compare wrote its right operand to a zero-page local before reading it back. The opcode the compiler needed was sitting in the encoding table, waiting for a dispatch arm that nobody had written.

Project c6502 Target Apple II beam state machine Bug class back-end addressing-mode gap Result 5 bytes / 8 cycles per occurrence; three example files shrank

Two assemblers, one comparison

The C source was a single line out of the beam state machine's attack-phase dispatch:

if (beam_y == floor_y_table[floor_idx]) {
    beam_state = 0x00;
    return;
}

Two reads, one compare, one branch. The hand-written 6502 for the same logic packed it into four instructions:

        AND #$0F                  ; extract floor idx from state
        TAX
        LDA BEAM_Y
        CMP FLOOR_Y_TABLE,X
        BNE .attack_step          ; not yet at floor row

c6502 produced this:

   AND   #$0F
   TAX
   LDA   floor_y_table,X
   STA   __local_beam_target_tick__0
   LDA   beam_y
   CMP   __local_beam_target_tick__0
   BNE   .if_end@2

The two highlighted lines are a memory ping-pong: load the table entry into A, then immediately store it to a function-local byte at $84, only to read it back two instructions later. Both the load and the store address byte-sized memory that CMP can address directly. The compiler was paying five bytes and eight cycles to stage a value that the comparison instruction could have read in place.

This isn't an exotic case. It's what c6502 emits for every equality compare. The fix turned out to be a few lines in one place and a small peephole pass in another — but only after admitting that the lowering wasn't wrong, it was just optimistic about what the back end could consume.

Why the temp existed

c6502's TAC stage lowers a binary equality test by reading the right-hand side into a value-temp, then the left-hand side into another, then comparing the two:

t0 = floor_y_table[floor_idx]
t1 = beam_y
t2 = (t1 == t0)
JumpIfZero(t2, .if_end@2)

The two operand temps fall into one ZP slot apiece. When the asm-level pipeline lays out those slots, t0 gets the local byte at $84, t1 gets coalesced into A (it's the immediate operand to the compare, and there's no reason to spill it), and the compare gets lowered as CMP against t0's slot.

That's how every other equality compare in c6502 works too. x == 3 doesn't trip the pattern because 3 never gets a temp — it's an immediate. x == y for two scalars in static storage trips a degenerate form of it, but copy propagation usually collapses one side back into the LDA before emit. The shape that survives all the way to the asm output is "the RHS is something whose addressing mode the back end can't fold into the CMP — so it stages through a memory cell first".

The motivating C, beam_y == floor_y_table[floor_idx], lowers the RHS as an indexed array read. That's IndexedData in the asm IR — addressed as LDA name+off,X or LDA name+off,Y on the chip. Both are valid 6502 addressing modes. CMP has both of them too: CMP $XXXX,X at opcode 0xDD, CMP $XXXX,Y at opcode 0xD9. The encoding table in the emitter knew this:

# Absolute,X (3 bytes: opcode + lo + hi)
_ABSX = {
    "LDA": 0xBD, "STA": 0x9D,
    "ADC": 0x7D, "SBC": 0xFD,
    "AND": 0x3D, "ORA": 0x1D, "EOR": 0x5D,
    "CMP": 0xDD, "LDY": 0xBC,
    "ASL": 0x1E, "LSR": 0x5E, "ROL": 0x3E, "ROR": 0x7E,
    "INC": 0xFE, "DEC": 0xDE,
}

But the function that dispatched Compare operands to addressing modes didn't:

match right:
    case asm_ast.Imm(value=v):
        ...
    case asm_ast.ImmLabelLow() | asm_ast.ImmLabelHigh():
        ...
    case asm_ast.Data() | asm_ast.ZP():
        return [_instr_line(opcode, _abs_addr(right))]
    case asm_ast.Stack() | asm_ast.Frame():
        ...
    case asm_ast.Indirect(offset=off):
        ...
    case asm_ast.IndirectY():
        ...
    case asm_ast.IndirectZp(...):
        ...
    case asm_ast.IndirectZpY(...):
        ...
    case _:
        raise ValueError(
            f"cannot emit Compare(left={left!r}, right={right!r})"
        )

IndexedData isn't in the match. Nine operand kinds, eight dispatch arms, one missing. When the asm-level optimizer offered CMP IndexedData, the emit table would have happily encoded it — but the emitter raised before that ever got a chance. So upstream passes never produced the shape, downstream peepholes never saw it, and the lowering always staged through a temp.

Pattern

Encoding tables and dispatch functions drift independently. The encoding table is data, edited once when the ISA is set up; dispatch functions are written one operand kind at a time, in response to whatever the lowering currently produces. The set of (operand × instruction) pairs the table can encode is always a superset of what dispatch handles, and the gap is where opportunities for code-shape changes hide.

Three lines of dispatch

The fix in the emitter was three lines:

case asm_ast.Data() | asm_ast.ZP():
    return [_instr_line(opcode, _abs_addr(right))]
case asm_ast.IndexedData():
    if opcode != "CMP":
        raise ValueError(...)
    return [_instr_line(opcode, _indexed_data_addr(right))]
case asm_ast.Stack() | asm_ast.Frame():
    ...

The CPX and CPY guard exists because the 6502 doesn't have an indexed form of those — there's no CPX abs,Y. Only CMP (the A-side compare) has the indexed modes. The guard documents that, and turns a silent encoding error into a loud one if a future pass ever produces Compare(X, IndexedData).

An identical edit went into the in-process simulator's assembler, which has its own copy of the same dispatch (different code, same shape — the simulator emits to a memory image rather than a text file, and they share the encoding tables but not the dispatch logic). Adding IndexedData to only one of the two would have meant the optimizer's text output worked but the simulator couldn't run it, which is exactly the failure mode that a prior memory entry — about emit dispatch lagging opcode tables — warns me to check both sides.

With dispatch in place, the optimizer was free to produce CMP IndexedData. But it didn't, because no pass had ever needed to construct one — the existing copy-prop / DSE passes only knew how to drop or substitute, not how to reshape four instructions into two.

The four-instruction window

The peephole that recognizes the shape is short. Match four consecutive instructions:

LDA   src        ; Mov(, Reg(A))
STA   tmp        ; Mov(Reg(A), )
LDA   other      ; Mov(, Reg(A))
CMP   tmp        ; Compare(Reg(A), )

And rewrite to:

LDA   other
CMP   src

The semantic argument is straightforward. After the original sequence, A holds other and the flags reflect A - tmp. Since tmp was just written from src and the only instruction in between (the LDA of other) doesn't write to memory, tmp's value equals src's value at the CMP. CMP tmp and CMP src produce the same flag set. After the rewrite, A still holds other; flags still reflect A - src; downstream observers see no difference.

The dropped STA tmp would have written a byte that the original code then immediately re-read at the CMP. With the rewrite, tmp is no longer written and no longer read. If tmp was used only by this comparison — and in c6502's lowering it usually is, because each temp is a fresh slot per comparison — its zero-page byte becomes dead. The general dead-store pass collects it; the slot allocator stops emitting an EQU for it.

Eligibility, conservatively

The rewrite is sound on the headline case but has corners. Three of them mattered enough to write checks for; the rest get covered by "if any check fails, leave the four instructions alone".

Source addressing-mode support. The rewritten CMP has to be encodeable. CMP can use Imm, ImmLabel, Data, ZP, IndexedData, Stack, Frame, Indirect, IndirectY, IndirectZp, IndirectZpY — most of LDA's modes. The peephole restricts itself to the first five (Imm through IndexedData), which covers every case the lowering actually produces today. The frame-relative and indirect modes are reachable in theory; the peephole leaves them to a future extension that can convince itself the LDY setup they emit doesn't clobber state the CMP needs.

Index register clobber. IndexedData(name, off, Y) reads Y at access time. If the intervening LDA — the one loading other — emits an LDY #off as part of its addressing-mode setup, Y won't hold the same value at the rewritten CMP that it held at the original LDA of src. The check is: when src indexes through Y, reject if other is one of the Frame / Stack / Indirect / IndirectZp modes that emit a load of Y. Indexing through X is always safe — no LDA addressing mode writes X.

Other / tmp aliasing. If other happens to read the same byte that tmp names, the rewrite breaks the load order. In the original sequence, LDA other reads tmp after STA tmp wrote it — so A holds src's value. In the rewritten sequence, LDA other reads tmp with no preceding STA, so A holds whatever tmp held before. Different program. The check is: if both are Data or ZP, accept only when their structural identities differ; for any indirect / indexed other, reject (the bytes they read can't be pinned at compile time).

The corner-case set is small but worth a table in the comment block. The peephole's actual code body is around 30 lines:

def _matches_pattern(a, b, c, d) -> tuple[Operand, Operand] | None:
    if not (
        isinstance(a, Mov) and not a.is_volatile
        and _is_reg_a(a.dst)
        and isinstance(b, Mov) and not b.is_volatile
        and _is_reg_a(b.src) and _is_stable_mem(b.dst)
        and isinstance(c, Mov) and not c.is_volatile
        and _is_reg_a(c.dst)
        and isinstance(d, Compare)
        and _is_reg_a(d.left) and _is_stable_mem(d.right)
    ):
        return None
    src, tmp_sta, other, tmp_cmp = a.src, b.dst, c.src, d.right
    if not _operands_equal(tmp_sta, tmp_cmp): return None
    if not _src_eligible(src): return None
    if (isinstance(src, IndexedData)
            and isinstance(src.index, Y)
            and not _y_safe_other(other)):
        return None
    if not _other_alias_safe(other, tmp_sta): return None
    return src, other

Five guards, all rejection-mode. When they all pass, the rewrite is mechanical: emit a new LDA other, a new CMP src, skip the four matched instructions, continue.

The local that vanished

Running the new pass over the example corpus, three files shortened: beam_target_tick by two lines, companion_update by thirteen, and do_ascend by thirteen.

The first two were direct hits — each had one or more of the exact four-instruction window, and each window collapsed into two instructions plus the drop of a per-comparison local. The byte-and-cycle ledger was easy to read off the diffs.

do_ascend's diff was bigger than the others because of a secondary effect. The C is:

uint8_t col = player_col;
if (col == floor_ceil[asc_floor]) {
    ...
}
col = (uint8_t)(col - 0x04);
player_col = col;
if (col == floor_ceil[asc_floor]) {
    ...
}
if (col == floor_thresh[asc_floor]) {
    ...
}

col is read once into a local, then used three times: two compares against floor_ceil[X] and one against floor_thresh[X]. In the unoptimized form, each of those compares produced its own LDA-STA-LDA-CMP window, and each rewrote independently. So far so unsurprising.

What surprised me was what happened next. After all three windows collapsed, the only thing referencing the col local was the initial STA col that put player_col into it. With the three CMPs no longer reading col, the STA had nothing to feed. The dead-store pass collected it. The local-slot allocator noticed it had no users. The EQU __local_do_ascend__col $85 line at the top of the file disappeared.

The cascade is mechanical: collapse one instruction window, the value that window staged through becomes useless, the value's storage becomes useless, the storage's declaration becomes useless. Five lines turn into one line; the slot vanishes from the symbol table.

Side effect

A four-instruction peephole that drops one local per occurrence can also drop the local that fed the compared value, if that local was kept alive only by the compares. The cascade is invisible from the peephole's own implementation — it shows up in the diff against the previous snapshot, two passes later.

Why this generalizes

The reason this peephole works at all is that the four-instruction shape isn't an accident of one C source — it's the c99-to-TAC lowering for any equality compare whose right-hand side doesn't immediate-fold. Every arr[idx], *ptr, or non-static struct field on the right of == or != goes through the same pattern: read RHS, stage it, read LHS, compare. Until something downstream collapses it.

The full list of "things that stage on the right" includes, in c6502 today:

  • Array reads: x == arr[i], x == table[idx]. The motivating case. Lowers as IndexedData source.
  • Pointer deferences: x == *p. Lowers via indirect addressing, which the current peephole rejects (the indirect setup is non-trivial to preserve through a rewrite).
  • Compound expressions: x == (a + b). The sub-expression already gets a temp; the equality compare just reads it. Often handled by the existing copy-folding passes before this peephole sees the IR.
  • Static-storage reads: x == another_static. Two LDA-from-Data forms. Usually folded by copy propagation, but the four-instruction window matches and the peephole handles it.

The peephole catches the first and the last; the middle two are still on the table but require more invariants than the rewrite-as-written can prove. Cumulatively, the cases the peephole does catch turn out to be the bulk of the equality compares in the corpus that weren't already short.

What's pleasant is that all of this falls out of a single observation: c99 says "evaluate the right operand and the left operand of == in some order, then test for equality". c6502's TAC picks "right then left". The asm-level rewrite then picks "actually, no — left into A, compare directly against right". Both forms produce the same answer; the second is shorter. The order was an artifact of the IR's value-temp discipline, not anything semantically required.

What it taught

1. Lowering optimism is a real cost. The TAC stage was right to lower the comparison the way it did — uniformly, without trying to predict back-end addressing modes. The cost of that uniformity is exactly this kind of staging: a value moves through a temp because the lowering doesn't know whether the comparison can consume it directly. The fix isn't to make TAC peek at the back end; it's to give the back end a peephole that recognizes the staging and reshapes it.

2. Encoding tables outrun dispatch. An encoding table is set up once, tries to be comprehensive, and stays static. A dispatch function grows one arm at a time, only when a lowering pass produces a shape that hits it. The gap between the two — operand × instruction combinations the table can encode but dispatch never sees — is where opportunities live. The way to find them isn't to read the dispatch (it'll look complete by inspection); it's to look at the encoding table and ask, "for each row, do I have a dispatch arm that uses it?".

3. Peepholes have downstream cascades. Two instructions saved per match is the first-order story. The second-order story is the dead temp, the dead local, the dropped EQU, sometimes the dropped STA that fed the temp. None of that is in the peephole's code or comments; it's the natural composition of the existing dead-store and slot-allocation passes against the new shorter shape. The diff is the only place those second-order effects show up, and they're the most satisfying part to read.

The win on the headline example is five bytes and eight cycles per attack-phase tick of the beam. The win across the corpus is more like 28 lines of assembly and three unused zero-page slots. Both numbers are smaller than the impression the diff leaves. The diff shows a compiler getting visibly less apologetic — emitting the comparison the human would have written, against the addressing mode the chip was always willing to use.
