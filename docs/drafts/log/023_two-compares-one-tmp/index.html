Compiler log · #023

Two compares, one tmp

A peephole that dropped the only store to a memory cell without checking whether anyone else was still reading from it. The miscompile was silent — the asm was syntactically valid, the simulator ran it without complaint, and the only signal was a game-logic branch that never fired.

Project c6502 Target Apple II beam state machine Bug class peephole soundness, sole-writer drop Surfaced by one new example, ten scenarios, a sim differential

A silent miscompile

The example was beam_target_draw — the routine that paints the beam's trail and runs a four-slot enemy collision check. Five passes per call: gate on idle, compute height to the target row, draw the trail, walk slots 3..0 looking for one whose screen column lands in the beam's two-pixel band, and trigger the hit if it does.

The sim-differential harness exercises ten scenarios: idle, target-reached, chase-without-enemies (two height-clamp boundaries), three flavors of hit (slot 3, slot 0, slot-3-shadows-slot-0), and three flavors of near-miss (column too low, row out of range, inactive flag). The unoptimized pipeline matched all ten expected snapshots. The optimized pipeline diverged on three of them — every scenario that should have fired the hit branch.

!!! s5: opt=03800000000001000003020424804000
        exp=00800a000000000103020424804001
!!! s6: opt=038000aa000000000004020424800000
        exp=00800a000000000104020424800002
!!! s7: opt=03800055000055000005020424800000
        exp=00800a55000000000105020424800003

In each diverging case the optimized output had beam_state = 0x03 (unchanged from input — the hit clears it to 0x00), beam_snd_ctr = 0x00 (the hit sets it to 0x0A), and a score_calls counter stuck at zero. The enemy was unscathed; its flag was still 0xFF. The beam drew its trail and walked off without noticing the target right under it.

The asm for the hit-detection loop, after --optimize:

.loop@0_start:
   LDA   enemy_flag,Y
   BEQ   .loop@0_continue
   LDX   enemy_col,Y
   LDA   #$25
   CMP   proj_screen_col,X
   BCC   .loop@0_continue
   LDA   #$23
   CMP   __local_beam_target_draw__state
   BCS   .loop@0_continue

The two highlighted lines are the two halves of the C-source band check:

uint8_t screen_col = proj_screen_col[enemy_col[slot]];
if (screen_col > 0x25)  continue;
if (screen_col <= 0x23) continue;

The first comparison is reading proj_screen_col,X directly. The second is reading __local_beam_target_draw__state — a function-local zero-page slot that earlier in the routine held the post-clamp height value (0x01, 0x02, 0x03, or 0x04). The chip dutifully compared 0x23 against whatever stale byte was sitting in that slot from the height computation. The branch decision then depended on the height the routine had drawn with — which is unrelated to the enemy's screen column, so it answered the wrong question every time.

The two comparisons are supposed to be testing the same value: screen_col. Some peephole earlier in the pipeline had rewritten the first compare to read from the indexed table directly, but had forgotten that the staging slot it was retiring was still being read by the second.

The shape that broke it

The peephole was cmp_through_tmp_fold — the one introduced in log/021. It looks for a four-instruction window:

LDA   src       ; Mov(, Reg(A))
STA   tmp       ; Mov(Reg(A), )
LDA   other     ; Mov(, Reg(A))
CMP   tmp       ; Compare(Reg(A), )

and rewrites it to two instructions:

LDA   other
CMP   src

The rewrite drops the LDA src (its only purpose was to feed the temp) and the STA tmp (the temp is no longer needed because the new CMP reads src directly). The intuition is that tmp exists only to bridge the LDA src and the CMP; with the CMP now reading src, the bridge is dead.

That intuition holds in every case the pass was designed for. The motivating shape from beam_target_tick — beam_y == floor_y_table[idx] — produces exactly one such window, with exactly one STA feeding exactly one CMP. Drop the window, drop the slot, save five bytes and eight cycles. Three example files shrank when the pass shipped.

The C source from beam_target_draw produces a different shape:

uint8_t screen_col = proj_screen_col[enemy_col[slot]];
if (screen_col > 0x25)  continue;
if (screen_col <= 0x23) continue;

screen_col is loaded once and then compared twice. The TAC lowering, faithfully, stages it through a local exactly once and reads from that local twice:

   LDA   proj_screen_col,X     ; load screen_col into A
   STA   __local_*             ; stage into tmp
   LDA   #$25                  ; first comparison: $25 vs screen_col
   CMP   __local_*
   BCC   continue
   LDA   #$23                  ; second comparison: $23 vs screen_col
   CMP   __local_*
   BCS   continue

The peephole scanned forward, found the first four-instruction window (LDA proj_screen_col,X; STA tmp; LDA #$25; CMP tmp), matched it, and rewrote it. The second CMP tmp wasn't part of any matched window — there's no STA tmp immediately before it — so the scan walked right past it. The rewrite dropped the only STA tmp the pass had visibility into. The second CMP kept reading tmp; the slot held whatever the regalloc had put there earlier; the branch decision was nondeterministic-looking but deterministically wrong.

The unstated assumption

The pass's docstring said this about soundness:

The rewrite drops both the LDA src and STA tmp. After the rewrite, tmp becomes dead-after-rewrite; downstream asm_dead_store handles any remaining STAs to tmp elsewhere in the function.

"Dead-after-rewrite" was the assumption. It held for every case the author had thought to test. It also held for every existing example in the corpus, because the lowering that produces the staging shape almost always uses each staged value exactly once — the value-temp discipline that gave the temp its own slot is the same discipline that makes the slot a write-once / read-once cell.

The exception is when one C expression is reused across two compares without an intervening assignment. screen_col in the band test is one example; any x == A && x == B shape would be another; so would if (x > LO && x < HI) with x as an indexed read. The TAC lowering, sensibly, doesn't re-load x for each compare — it loads it once into a temp and reads the temp twice. The peephole sees the first read, rewrites it, and silently breaks the second.

The dead-store pass doesn't help. Its job is to drop writes whose value is unread. Here the value is read — by the orphaned second CMP. The store is being dropped not by dead-store but by cmp_through_tmp_fold itself, before dead-store ever runs. There's no consumer of the rewrite that's positioned to notice that one of the original readers got cut off.

Bug class

A peephole that's the only writer of a memory cell within its pattern must verify that nothing else in the function still reads that cell. If something does, the rewrite drops a store whose value those other readers depend on — and they'll quietly read whatever was in the slot from a prior use. The miscompile is silent because the asm is syntactically and structurally fine; the only sign is a runtime value drift that depends on what the regalloc had previously parked there.

First fix, over-conservative

The natural fix is to gate the rewrite on an eligibility check: before dropping the STA tmp, verify that no other instruction in the function references tmp. If something does, bail.

The first version of the check did exactly that, treating "reference" as "appears as any operand of any instruction":

# reject the fold if tmp appears anywhere outside the matched window
outside_uses = any(
    _references_tmp(other_instr, tmp)
    for j, other_instr in enumerate(instrs)
    if j < i or j > i + 3
)
if not outside_uses:
    # ...rewrite...

The two new failing unit tests for the bug passed immediately. The end-to-end sim differential for beam_target_draw went green. Both pipelines produced identical observable state across all ten scenarios. Confidence at this point was high.

The full test suite then surfaced two regressions in the snapshot tests for other examples — do_ascend grew from 68 lines to 81, and companion_update grew from 725 to 735. Neither was wrong, just longer. The check was rejecting folds that had been doing real work in those files.

Reads matter, writes don't

The first thing the diff for do_ascend showed was that the regressed examples weren't reading tmp elsewhere — they were writing it. The same slot was being reused for multiple short-lived temporaries:

LDA   floor_ceil,X
STA   __local_do_ascend__0     ; first compare's stage
LDA   __local_do_ascend__col
CMP   __local_do_ascend__0
   ...
LDA   floor_ceil,X
STA   __local_do_ascend__0     ; second compare's stage (overwrite)
LDA   __local_do_ascend__col
CMP   __local_do_ascend__0

Outside the first matched window, the slot appears as the destination of the second STA. That's a write — the original value the first window stored is overwritten before any other read happens. Dropping the first window's STA would be sound: the slot's value would be uninitialized between the rewrite and the second STA, but nothing reads it, so it doesn't matter.

The conservative version of the check treats writes and reads identically. That was over-rejection. The right check counts only reads — places where the slot's value flows out to something else (the src of a Mov, either operand of a Compare, the read side of a read-modify-write like INC or DEC). Refining the check to count only reads got companion_update's diff to zero — but do_ascend was still long.

Group by tmp, own every read

What do_ascend actually does is reuse the slot for three independent compares:

uint8_t col = player_col;
if (col == floor_ceil[asc_floor])    { ... }
col = (uint8_t)(col - 0x04);
player_col = col;
if (col == floor_ceil[asc_floor])    { ... }
if (col == floor_thresh[asc_floor])  { ... }

Each compare produces its own four-instruction window: LDA <table>,X; STA __local_*__0; LDA col; CMP __local_*__0. Three windows. Three STAs. Three CMPs. The slot is overwritten before each compare, so each compare reads the value its own window wrote. There are no orphan readers.

Folding any single window in isolation, with my read-counting check, still got rejected — because the OTHER two windows' CMPs are reads of the slot. The check sees three reads of tmp and only one is in the current matched window; it bails. None of the windows fold. The diff stays long.

The right check works across windows. Group all candidate windows by their tmp. For each group, every read of the slot in the function must sit at one of the group's matched CMP positions. When that holds, folding all the windows in the group as a batch leaves zero unowned readers — every read is rewritten away by some member of the group.

# enumerate all candidate windows
candidates = [(i, src, other, tmp)
              for i in range(len(instrs) - 3)
              if (m := _matches_pattern(...)) is not None]

# group by tmp; collect "owned" CMP positions per group
owned_cmp_idxs_by_key = {}
for i, _, _, tmp in candidates:
    owned_cmp_idxs_by_key.setdefault(_tmp_key(tmp), set()).add(i + 3)

# a group folds iff every read of its tmp lives at an owned position
foldable_keys = {
    key for key, owned in owned_cmp_idxs_by_key.items()
    if all((k in owned) or not _reads_tmp(instr, tmp_by_key[key])
           for k, instr in enumerate(instrs))
}

Under this check, do_ascend's three windows form a single group with three owned reads; every read of the slot in the function is owned; the group folds and the three local-store-and-CMP pairs collapse to three direct CMP <table>,Xs. beam_target_draw's back-to-back band check forms a one-candidate group with one owned read, but the slot has two reads in the function — only one is owned, so the group bails and the staging stays in place. The asm grows slightly compared to the (incorrect) pre-fix output, and the second CMP reads from a slot that's actually been written.

What it taught

1. The dangerous peepholes are the ones that drop a write. A peephole that drops an arithmetic instruction is easy to reason about — the value isn't needed, so removing the producer is safe. A peephole that drops a store is reasoning about other parts of the program too: every reader of the cell the store was feeding. If the pattern is the only writer, every reader becomes the rewrite's responsibility. The pass either has to rewrite all of them or refuse the fold; quietly dropping the store and hoping nobody else needed it is the failure mode.

2. "Dead-after-rewrite" needs to be a check, not a comment. The original docstring asserted that the temp was dead after the rewrite. That assertion was true in every case the author had in mind. It was false in one case the author hadn't. The way to make sure the assertion holds is to verify it — walk the function, look for readers, only fold if none survive. Comments don't run; checks do.

3. The conservative version of a check is usually too conservative. "Reject the fold if tmp appears anywhere else" passes every soundness test but rejects too many real opportunities. "Reject the fold if tmp is read elsewhere" is tighter but still rejects every multi-window group that shares a slot. "Group windows by tmp and verify every read is owned by some window's CMP" is the level of specificity the actual rewrite needs. Each refinement is a step toward exactly capturing what the rewrite assumes about the surrounding code — no less, no more.

4. A test case is worth more than a proof. The bug was missed in the original review because the original review was thinking about the four-instruction window in isolation. It didn't occur to either of us that one STA could feed two CMPs — that's not a shape any pass produces on purpose, so it's not the kind of thing an inspection would surface. The thing that surfaced it was a new example exercising new C source, with a sim-differential test that compared opt to unopt and noticed the answer was wrong. Routine new-example writing turns out to be the most reliable bug-discovery tool the project has — better than reading the pass code, better than reading the asm output, better than anything else short of fuzzing.

The fix is six lines of group-collection and a one-line predicate. The miscompile it prevents is invisible from the asm and silent in the type checker. The difference between the right version of the eligibility check and the wrong one is the difference between four sound examples and four sound examples plus three that turn into a coin flip at runtime. There's no extra cleverness in the fix; the cleverness was in writing the test that found it.
