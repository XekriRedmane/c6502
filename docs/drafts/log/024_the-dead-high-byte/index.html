Compiler log · #024

The dead high byte

A two-instruction skeleton sitting in the middle of every uint8_t op uint8_t result: LDA #$00; SBC #$00, computing a value nobody reads. The asm-level dead-code pass can see almost every variant of this shape. The one variant it can't see is the one this routine happened to produce.

Project c6502 Subject C99 integer promotion residue Pass added narrow_widened_arith (TAC-level) Wins 3 examples, −8 instrs total, 2 locals freed

A line you can spot without context

Halfway through beam_target_draw, after computing the trail height as a difference between two byte tables, the asm goes:

   LDA   floor_y_table,X
   SEC
   SBC   beam_y
   STA   __local_beam_target_draw__state
   LDA   #$00
   SBC   #$00
   LDA   __local_beam_target_draw__state
   BNE   .if_end@1
   RTS

The first three instructions compute floor_y_table[X] − beam_y with carry-in seeded by SEC. The STA commits the low byte to a one-byte local. Then comes the headline: LDA #$00; SBC #$00, which would compute the high byte of a 16-bit subtraction... if anyone read it. Nobody does. The very next instruction is LDA __local_*__state, which loads the low byte back into A and walks straight into a BNE that tests Z from the load. The high-byte SBC's result, and every flag it set, dies on the floor.

That's two bytes of code and three cycles per call doing nothing. The shape is local enough that you don't have to know the routine to spot it: any time you see LDA #$00; SBC #$00 (or LDA #$00; ADC #$00) followed by an unconditional re-load of A without a flag-consuming instruction in between, you're looking at a dead high byte.

Why it's there

The C source for the computation is one line:

uint8_t delta = (uint8_t)(floor_y_table[floor_idx] - beam_y);

Both operands are uint8_t. The subtraction promotes them to int per C99 §6.3.1.1, computes the result at int width, and the explicit cast truncates back to uint8_t. At TAC the rendering is exact:

ZeroExtend(floor_y_table[floor_idx] -> %a:int)
ZeroExtend(beam_y                    -> %b:int)
Binary(Subtract, %a, %b               -> %r:int)    # 16-bit subtract
Truncate(%r                           -> %d:uchar)  # cast back to 1 byte

The asm lowering can't shed the widening on its own. Binary(Subtract, ..., ..., %r:int) is a two-byte subtract; tac_to_asm dutifully emits the per-byte chain. The Truncate downstream drops the high byte by simply not loading it back, but the high-byte SBC has already been emitted by then. The STA commits only the low byte, the high byte's destination is the live A register, and the very next instruction overwrites that A with the truncated value the routine actually wants.

This is the shape that's everywhere in C-targeting-an-8-bit-machine code. Every uint8 + uint8, uint8 - uint8, uint8 & mask, uint8 | bits that gets stored or compared as uint8 goes through it. If the compiler doesn't kill the widening somewhere along the way, it ships as a 6502 routine that does roughly twice the work it should.

Why the asm-level pass can't always drop it

c6502 has an asm-level peephole, dead_a_arith, whose whole job is to drop instructions whose only effects are writes to A and the N/Z/C/V flags, when both A and the flags are dead afterward. Its motivating case was almost exactly the shape above — and the pass iterates a local fixed point so a single sweep can drop the trailing atom of a chain, then a follow-up sweep drops the LDA the chain previously kept alive.

To drop an SBC, dead_a_arith needs all four of N/Z/C/V dead at the position right after it. The N/Z check has a forward-walk helper, flags_dead_at, that returns true if no Branch reads N/Z before some later flag-setter overwrites them. The all-four check is stricter: all_flags_dead_at also bails when it sees an instruction that reads C or V (subsequent ADC/SBC on a carry chain, ROL/ROR using C as the shift-in bit). And both functions bail at any Branch, because they don't know which flag the Branch consumes.

That last detail is the trap. In the snippet above, the sequence after SBC #$00 is LDA mem; BNE .if_end@1:

  • N, Z — the LDA overwrites them. Dead from the SBC's perspective.
  • C, V — the LDA doesn't touch them. They survive past the load and reach the BNE.
  • The BNE reads only Z, which is from the LDA, not the SBC. Nobody reads C or V before they're overwritten again (downstream, the CMP #$05 rewrites C).

So C and V from the SBC are genuinely dead — but proving it requires knowing that the BNE reads only Z, not C/V, and that downstream paths overwrite C before anyone reads it. The current all_flags_dead_at doesn't carry that bookkeeping. It sees the Branch and returns False. The SBC stays.

Refining the helper is doable — track per-flag liveness, walk forward through the CFG, intersect at joins. But it's a bigger lift than the headline case warrants, and it doesn't address the underlying problem: the wasted SBC was generated in the first place because TAC carried the widening through to the asm boundary.

Two places to fix it

That left two clean options:

LayerApproachCatchesCost
asm Refine all_flags_dead_at to track per-flag liveness across branches. Any dead-flag arith, regardless of how it got there. Cross-block dataflow for C and V; intersections at joins; care with V's V-correction patterns.
TAC Recognize Truncate(Binary(safe_op, Extend, Extend|Const)) and rewrite to a narrow Binary at the truncate's width. Every uint8 op uint8-style cast-back-to-narrow in the source, before asm lowering gets a chance to widen the work. Per-op soundness reasoning; a structural pass similar to the existing truncate_extend_fold.

The TAC fix is the broader generalization. It kills the work at the source — no widened Subtract is ever emitted, so no dead high-byte SBC exists to drop later. The asm-level refinement is a downstream sweep that would always be playing catch-up.

Which ops are safe to narrow

The TAC rewrite says: Truncate(Binary(op, Extend(a), Extend(b)), u_n) is equivalent to Binary(op, a, b, u_n) at the narrow width, whenever the low n bytes of op(extend(a), extend(b)) depend only on the low n bytes of extend(a) and extend(b). Modular arithmetic, in other words.

For 6502, that gates the list cleanly:

OpLow byte depNarrowable?Why
Addcarry flows low→highyesResult's low n bytes are the n-byte add of the low n bytes of the operands.
Subtractborrow flows low→highyesSame as Add. The 6502 borrow direction matches modular arithmetic.
Multiplypartials sum into lowyesTwo's-complement and unsigned multiply agree mod 28n; low n bytes depend only on low n bytes.
BitwiseAndper-byteyesTrivial: each byte is independent.
BitwiseOrper-byteyesSame.
BitwiseXorper-byteyesSame.
Dividehigh bytes feed quotientnoLong-division partials pull from the high bytes; narrowing changes the answer.
Modulosame as DividenoSame.
RightShifthigh bytes shift into lownoA right-shift moves data downward; truncating after preserves bits the narrow op would have lost.
LeftShiftnonesafe but deferredLow bytes are independent of high bytes for left shift, but the 6502 shift helpers consume only one byte of the count anyway, so the high-byte work is already cheap. Marginal win; revisit if a motivating case appears.

For constant operands, the modular-arithmetic argument extends without conditions — narrowing a Constant to the target width is just masking modulo 28n. Subtract(extend(a), 0x1234) truncated to uchar equals Subtract(a, 0x34) at the narrow width, because 0x1234 mod 256 = 0x34 and modular arithmetic preserves the equivalence.

The pass

The new pass, narrow_widened_arith, sits in the TAC fixed-point loop next to the existing truncate_extend_fold. The two are structural siblings:

  • truncate_extend_fold matches Truncate(Extend(x)) with nothing between — the identity round-trip. Replaces with a Copy (or a narrower Truncate if dst is narrower than the original source).
  • narrow_widened_arith looks through a single Binary in the middle. Matches Truncate(Binary(safe_op, Extend(a), Extend(b)|Const)). Rewrites the Truncate to a narrow Binary at the target width, leaving the original Binary and Extends for SSA-DCE to collect.

The single-pattern soundness story is local: the rewrite only changes what's at the Truncate position. The original Extends and Binary stay in place; if they have other consumers they survive, if not, the next sweep drops them. The pass doesn't have to reason about whether the widened values are needed elsewhere — that's SSA-DCE's job.

# before
ZeroExtend(a   -> %ea:int)
ZeroExtend(b   -> %eb:int)
Binary(Subtract, %ea, %eb -> %r:int)
Truncate(%r -> %d:uchar)

# after one pass
ZeroExtend(a   -> %ea:int)               # now dead
ZeroExtend(b   -> %eb:int)               # now dead
Binary(Subtract, %ea, %eb -> %r:int)     # now dead
Binary(Subtract, a, b -> %d:uchar)       # the narrow form

# after SSA-DCE on the next iteration
Binary(Subtract, a, b -> %d:uchar)

Soundness gates: both Extends' dsts and the Binary's dst must be SSA-renamed names (their single-def guarantee is what makes the def chain unambiguous); the Binary's dst width must be strictly wider than the Truncate's dst width; each Extend's source width must match the Truncate's dst width. The pass is a no-op without ssa_dsts or the symbol table.

The instruction that came back

The first run of the full test suite after the pass landed surfaced four gold-output mismatches. Three were the wins we wanted — beam_target_draw dropped its dead LDA #$00; SBC #$00; LDA local triple, companion_update dropped the same shape at another site, and beam_target_tick shrank by one instruction with two locals collapsed away by a downstream cascade. The fourth was a regression: apply_bobble grew by one instruction.

apply_bobble's C source has this shape:

uint8_t bobble    = rescue_bobble[bobble_idx];
uint8_t magnitude = bobble & 0x7F;
if (bobble & 0x80) {
    entity_floor_pos[slot] = (uint8_t)(entity_floor_pos[slot] + magnitude);
} else {
    entity_floor_pos[slot] = (uint8_t)(entity_floor_pos[slot] - magnitude);
}

Before the new pass, the optimized asm was:

   LDA   rescue_bobble,X
   BPL   .if_else@1          # tests sign of bobble
   AND   #$7F                # then-branch: A = magnitude
   CLC
   ADC   entity_floor_pos,Y
   STA   entity_floor_pos,Y
   JMP   .if_end@0
.if_else@1:
   AND   #$7F                # else-branch: A = magnitude
   STA   __local_apply_bobble__1
   LDA   entity_floor_pos,Y
   SEC
   SBC   __local_apply_bobble__1
   STA   entity_floor_pos,Y

The trick: magnitude is computed inside each branch, not before. The BPL tests the sign bit of bobble directly from the LDA's flags, then each branch redoes the AND #$7F to derive magnitude. The then-branch keeps magnitude in A and adds entity_floor_pos[Y] from memory; the else-branch has to subtract magnitude from entity_floor_pos[Y], so it stashes magnitude to a local first.

After the new pass, the asm changed to:

   LDA   rescue_bobble,X
   AND   #$7F
   STA   __local_apply_bobble__1     # magnitude computed before the branch
   LDA   rescue_bobble,X            # reload bobble to test sign
   BPL   .if_else@1
   LDA   entity_floor_pos,Y
   CLC
   ADC   __local_apply_bobble__1
   ...

One AND, one STA, one reload of bobble to recover its sign bit for the BPL. Net: +1 instruction.

The new pass had narrowed the magnitude computation into a single Binary(BitwiseAnd, bobble, 0x7F:uchar, %magnitude) at TAC level. That fold is sound and locally a win. But it changed the shape of the IR that a downstream pass — sink_and_past_branch — was looking for.

The ordering rule

sink_and_past_branch is the pass that produces the duplicated-AND-per-branch pattern. Its match window is a strict four-instruction adjacency:

ZeroExtend(%x, %x_ext)
Binary(BitwiseAnd, %x_ext, ConstInt(C), %x_and)
Truncate(%x_and, %t)
JumpIfMasked(%x, _, _, target)              # block terminator

When the window matches, it mints fresh per-branch SSA names for the trio, duplicates the trio into the start of both successor blocks, and drops the original. Each successor now computes magnitude independently from bobble — and the asm-level pipeline reduces each duplicated trio to AND #$7F in its own branch, with bobble's live range cut down to the LDA that feeds the BPL.

That window has three load-bearing parts: the leading ZeroExtend, the middle Binary(BitwiseAnd, _, ConstInt), and the trailing Truncate. narrow_widened_arith collapses all three into a single Binary(BitwiseAnd, bobble, ConstUChar(0x7F), magnitude) at the narrow width. To sink_and_past_branch, the new shape is unrecognizable. It sees a single Binary followed by a JumpIfMasked — no leading ZeroExtend, no trailing Truncate — and skips. The narrowed Binary stays before the branch, magnitude has to live across the test, and the asm-level lowering writes it to a local because there's no other place for it to go.

The fix was one line of ordering. narrow_widened_arith moves to after sink_and_past_branch in the fixed-point loop:

fn = fold_truncate_extend(fn, ...)
fn = sink_increments(fn)
fn = sink_and_past_branch(fn, symbols=symbols)
fn = narrow_widened_arith(fn, symbols=symbols, ssa_dsts=ssa_dsts)

Now in iteration 1: sink_and_past_branch matches the wide trio first and duplicates it into the successor blocks; then narrow_widened_arith sees the duplicated trios — one in each successor — and narrows each independently. The result is the optimal shape: AND #$7F recomputed inside each branch, no precomputation across the branch, no live range spanning the test. apply_bobble's asm went back to its original length.

Cross-pass dependency

Any TAC pass that simplifies the ZeroExtend · BitwiseAnd · Truncate shape has to run after sink_and_past_branch. The latter's pattern is strict — the simplified form doesn't match it — and the duplication-into-both-branches win is fragile. This is the kind of constraint that doesn't show up in a docstring of either pass, only in the gold-output diff of apply_bobble.

What landed

With the ordering settled, the three wins are clean:

ExampleΔ instrsNotes
beam_target_draw −3 The motivating case. The dead LDA #$00; SBC #$00; LDA local triple is gone; a downstream peephole then noticed the STA local; BNE pair could test A directly, so the trailing LDA local went away too.
companion_update −4 Same pattern at another site — the same 16-bit subtraction lowering, the same dead high byte. The pass kills it without knowing or caring which routine produced it.
beam_target_tick −1, −2 locals The instruction count win is small, but the local-byte count went from 3 to 1. Two locals were holding intermediate high-byte staging that the dead-arith elimination caused subsequent passes to recognize as unused. The cascade rewrote a TXA-then-AND into AND-after-pre-TXA, and the saved locals would otherwise have been ZP bytes spent on stashing values that nobody read.

Total: 8 fewer instructions across the corpus, 2 ZP bytes freed for other functions to use, no regressions in the 2819-test suite. The 18 new unit tests for the pass cover the safe ops, the unsafe ops, constant narrowing (including the modular-reduction case and a negative signed constant), and the non-SSA-name soundness gates.

What it taught

1. The dead high byte is a C-targeting-an-8-bit-machine signature. Any C compiler that lowers uint8_t op uint8_t through the spec's integer-promotion path, on a target whose natural width is one byte, will emit work for high bytes that the source code never asked for. Some downstream pass — at TAC, at asm, somewhere — has to put the work back. Knowing what the dead shape looks like (LDA #$00; SBC #$00 or LDA #$00; ADC #$00, sitting between a low-byte commit and a use that re-loads A) makes it spottable in the asm without context. That's a useful debugging eyeball: if you see it, the optimizer left something on the table.

2. TAC-level narrowing is the right place to fix it. The asm-level pass is structurally constrained by the per-flag bookkeeping cost. C from an SBC survives past an LDA, V survives past everything that isn't a CMP / shift / call, and a Branch reads only one of N/Z/C/V — the rest have to wait for the next overwriter. Tracking that across a CFG is doable but rarely worth the carry-cost compared to just not generating the work in the first place. The TAC rewrite is local: match a shape, write a narrower shape, let SSA-DCE clean up.

3. Modular arithmetic is the right soundness argument. "Does this op's low n bytes depend only on the operands' low n bytes?" is a sharper question than "is this op narrowable?" It admits a clear yes-list (Add / Subtract / Multiply / AND / OR / XOR) and a clear no-list (Divide / Modulo / RightShift), without per-op cleverness. LeftShift sits in the yes-list but stays on the bench because the asm helpers already consume only one byte of the count; the rule still gives a clean answer, the choice not to fire is a separate decision.

4. Pass ordering surprises live in the gold-output diff. The sink_and_past_branch dependency wasn't obvious from reading the new pass, or from reading sink_and_past_branch's docstring, or from any local soundness check. It showed up as one specific example growing by one instruction, in a test suite where the other 2818 cases were green. That asymmetry — a passing test suite with one boring-looking gold-mismatch — is the optimizer's normal mode of telling you about a missed interaction. The remedy isn't more local soundness checks; it's reading the diff carefully enough to ask why the gold grew. The answer is almost always a pass earlier in the pipeline that depended on the shape you just simplified.
