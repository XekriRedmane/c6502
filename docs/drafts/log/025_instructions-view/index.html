Compiler log · #025

instructions_view

A pattern-matching framework that walks back through SSA def-use chains has to see its own rewrites as it goes — or chained fusions leave dangling references and require multiple outer iterations to converge.

Project c6502 Subject DefUsePass framework design Pass reassoc_const (motivating case) Files passes/optimization/framework/defuse.py

The chained-fusion problem

Consider this C source, which appears in a video-game renderer that blits pixels into a known framebuffer layout:

static uint8_t * const hires_page1 = (uint8_t * const)0x2000;
static const uint16_t row_offsets[192] = { 0x000, 0x400, 0x080, ... };
static const uint16_t col_offsets[40]  = { 0x000, 0x100, 0x200, ... };

hires_page1[row_offsets[row] + col_offsets[col] + byte_idx] = value;

After the static-const fold replaces hires_page1 with Constant(0x2000) and the const-array-subscript fold resolves both table lookups to compile-time constants (say row_offsets[2] = 0x080, col_offsets[1] = 0x100), the TAC for the address computation looks roughly like:

Binary(Add, Constant(0x100), byte_idx_ext, %a)
Binary(Add, Constant(0x080), %a,            %b)
Binary(Add, Constant(0x2000), %b,           %addr)
Store(value, %addr)

Three runtime 16-bit Adds, computing 0x100 + 0x080 + 0x2000 + byte_idx. The three constants could collapse to a single 0x2180. One Add instead of three. The question is whether reassoc_const can get there in a single pass.

The pass lives in passes/optimization/reassoc_const.py. It's a DefUsePass — a subclass of the base in passes/optimization/framework/defuse.py that provides a structured way to walk from a USE site backward through the SSA def-use chain to inspect producers. The framework was designed specifically so each pass doesn't have to hand-roll def-index bookkeeping. The question is what happens when two fusable pairs appear in the same function, back-to-back.

What reassoc_const does

ReassocConstants matches every instruction of the form:

Binary(Add, Constant(C1), %inner, %outer)   # outer — the USE site

When it finds one, it walks back via the SSA def-index to the instruction that defined %inner. If that instruction is also a Binary(Add, Constant(C2), V, %inner) — with %inner used exactly once — it fuses the two into:

Binary(Add, Constant(C1 + C2), V, %outer)

The inner def is dropped atomically (via Rewrite.drop_defs, discussed later). The two constant additions collapse at compile time; the runtime work is one Add instead of two.

Applied once to the three-Add chain above, the first fusable pair is i=1 and i=0:

i=0: Binary(Add, Constant(0x100), byte_idx_ext, %a)
i=1: Binary(Add, Constant(0x080), %a,            %b)   # outer matches here
i=2: Binary(Add, Constant(0x2000), %b,            %addr)
i=3: Store(value, %addr)

The match at i=1 walks back to i=0 and fuses: %b = Constant(0x180) + byte_idx_ext. The next fusable pair is i=2 and the new i=1 result. Whether that second fusion fires in the same pass iteration — or forces another outer fixed-point loop — is the load-bearing design question.

The naive walk-back

A naive DefUsePass builds a def-index once from fn.instructions and hands it to the subclass's rewrite method via a DefUseEnv. Here is the naive shape:

def run(self, fn, ctx):
    def_idx = _build_def_idx(fn.instructions)
    env = DefUseEnv(def_idx=def_idx, instructions=fn.instructions)
    rewrites: dict[int, object] = {}
    drop_indices: set[int] = set()

    for i, instr in enumerate(fn.instructions):
        m = MatchResult()
        if not self.pattern.match(instr, m):
            continue
        result = self.rewrite(m, env, ctx)
        if result is None:
            continue
        rewrites[i] = result.replacement
        drop_indices.update(...)
    # rebuild ...

Walk through what happens to the three-Add chain under this design.

i=1: the pattern matches. env.def_of(%a) reads fn.instructions[0], gets Binary(Add, 0x100, byte_idx_ext, %a). Fuse: record rewrites[1] = Binary(Add, 0x180, byte_idx_ext, %b). Record drop_indices = {0}.

i=2: the pattern matches. env.def_of(%b) reads fn.instructions[1]. fn.instructions is immutable — it's the original list. So env.def_of(%b) returns the original Binary(Add, 0x080, %a, %b), not the fused form. The pass tries to fuse i=2 with that stale instruction. The inner operand would be %a from the original inner Add — but the rewrite at i=1 already dropped i=0, which defined %a. The combined Constant would be 0x2000 + 0x080 = 0x2080 (still wrong because we missed the 0x100), and the fused instruction would reference %a — a Var whose def was just dropped. Dangling reference.

The exact failure mode depends on the drop-conflict guard. If the guard fires (noting that %a's def index 0 is already in drop_indices), the second fusion is skipped entirely. The function exits the pass with one fusion done, two still needed. The outer fixed-point loop picks it up on the next iteration. Three-pair chains take two outer iterations; N-pair chains take N−1.

Failure mode

env.def_of(var) reads from the original fn.instructions. After a rewrite at i=1, the def-index for %b still points at the pre-rewrite form. A fusion at i=2 sees a stale producer — either producing a wrong result, or being blocked by the conflict guard.

The fix: instructions_view

The actual DefUsePass.run in passes/optimization/framework/defuse.py adds one list alongside the iteration:

def run(self, fn, ctx):
    if ctx.ssa_dsts is None:
        return fn
    def_idx = _build_def_idx(fn.instructions)
    instructions_view = list(fn.instructions)
    env = DefUseEnv(
        def_idx=def_idx,
        instructions=instructions_view,
        extra=self.prepare_extra(fn, ctx),
    )
    rewrites: dict[int, object] = {}
    drop_indices: set[int] = set()
    changed = False
    for i, instr in enumerate(fn.instructions):
        m = MatchResult()
        if not self.pattern.match(instr, m):
            continue
        result = self.rewrite(m, env, ctx)
        if result is None:
            continue
        if isinstance(result, Rewrite):
            # ... conflict guard ...
            rewrites[i] = result.replacement
            instructions_view[i] = result.replacement
            drop_indices.update(new_drops)
            changed = True
        elif result is not instr:
            rewrites[i] = result
            instructions_view[i] = result
            changed = True
    # rebuild from fn.instructions using rewrites / drop_indices
    ...

instructions_view starts as a copy of fn.instructions. After every successful rewrite, the framework immediately writes the new instruction into instructions_view[i]. env.instructions points at this same list — so any subsequent call to env.def_of(var) reads from the list as it exists after the rewrites already committed in this pass.

The outer iteration still walks the original fn.instructions (so the loop variable instr is always the original pre-rewrite form of instruction i, which is what the pattern should match). The rewrites dict and the final rebuild read from fn.instructions too, applying rewrites as overrides. But def-lookups read from instructions_view.

Walk through the three-Add chain again under this design.

i=1: pattern matches. env.def_of(%a) reads instructions_view[0] = original i=0. Fuse: rewrites[1] = Binary(Add, 0x180, byte_idx_ext, %b). Also: instructions_view[1] = Binary(Add, 0x180, byte_idx_ext, %b). drop_indices = {0}.

i=2: pattern matches. env.def_of(%b) reads instructions_view[1] = the fused form: Binary(Add, 0x180, byte_idx_ext, %b). The inner operand is now byte_idx_ext, not the stale %a. The inner constant is 0x180. Fuse with the outer constant 0x2000: produce Binary(Add, 0x2180, byte_idx_ext, %addr). Drop %b's def (the updated i=1). No conflict — the new drop index is 1, not 0.

Final rebuild: drop indices 0 and 1, replace i=2 with Binary(Add, 0x2180, byte_idx_ext, %addr). The output is:

Binary(Add, Constant(0x2180), byte_idx_ext, %addr)
Store(value, %addr)

Two instructions instead of four. A three-pair chain collapsed in a single pass. The outer fixed-point loop sees no change on the next iteration and moves on.

Result

Three sequential Add(Constant) pairs fuse to one in a single DefUsePass.run call. The instructions_view list is updated after each rewrite, so the next env.def_of lookup sees the already-fused form rather than the stale original.

The eager-drop angle

The mechanism above handles the READ side: lookups see the rewritten form. The WRITE side — actually removing the now-dead inner defs from the output — is handled by Rewrite.

A DefUsePass.rewrite method returns one of three things:

  • None — leave the instruction unchanged.
  • A plain instruction — replace the USE site. Leave any now-dead producers for DSE to collect on the next fixed-point iteration.
  • Rewrite(replacement, drop_defs=(var1, ...)) — replace the USE site AND atomically drop the defs of the named vars in the same rebuild pass.

For reassoc_const, returning a plain instruction would leave the inner Binary in the output. SSA dead-store elimination would remove it on the next iteration. That works, but it adds an outer iteration for every dropped def. For a post-fixed-point pass — one that runs after the main loop has converged and no further DSE will follow — leaving dead defs leaks IR into the asm lowering.

recognize_indirect_indexed is exactly that case. It's a post-fixedpoint one-shot (PostFixedpointPass) that collapses ZeroExtend(uchar) + Binary(Add, ptr) + Load into a single IndirectIndexed instruction for the 6502's (zp),Y addressing mode. There's no DSE after it. Without eager drops, the ZeroExtend and Binary would survive into tac_to_asm, which would lower them as real instructions despite their results being unused. Eager drops via Rewrite are what keep the asm output clean.

The conflict guard prevents double-drops when two rewrites in the same run call would both try to drop the same inner def:

if isinstance(result, Rewrite):
    new_drops: set[int] = set()
    for v in result.drop_defs:
        d = def_idx.get(v.name)
        if d is not None:
            new_drops.add(d)
    if new_drops & drop_indices:
        # Already claimed by an earlier rewrite — skip.
        continue
    rewrites[i] = result.replacement
    instructions_view[i] = result.replacement
    drop_indices.update(new_drops)
    changed = True

This guard is conservative: it rejects the second rewrite entirely rather than trying to merge the drops. In the chained case above, the drops are at different indices (0 and 1), so there's no conflict. If they did overlap — because two distinct USE sites both walked back to the same inner def — the second rewrite is simply deferred to the next fixed-point iteration, when DSE will have cleaned up the stale def and the conflict no longer exists.

Beyond reassoc_const

The instructions_view mechanism and the Rewrite return type are both general. Any pass built on DefUsePass gets them automatically. The design question for a new subclass is: do any two USE sites in the same function share a producer through the def-use chain?

If not — if every USE site's walk-back leads to a distinct producer — then instructions_view doesn't matter: no rewrite at i affects the producer seen at j. A plain instruction return is fine, and eager drops are optional (just a latency optimization against DSE).

If yes — if a USE site's producer is itself an instruction that was already rewritten earlier in the same pass — then instructions_view is load-bearing. The canonical example is exactly the chained Add shape: the outer USE at i=2 walks back through the producer at i=1, which was itself a USE site that just fired.

Two other DefUsePass subclasses in the optimizer are worth checking against this criterion:

PassPatternChain possible?Notes
FoldTruncateExtend Truncate(SignExtend|ZeroExtend(x)) No The USE is always a Truncate; the producer is always a cast. A Truncate is never itself the producer of another Truncate via this pattern.
NarrowWidenedArith Truncate(Binary(op, Extend(a), Extend(b))) No The USE is a Truncate; the two producers are a Binary and two casts. The narrow Binary the pass writes out is not itself the producer of any outer Truncate in the same chain.
ReassocConstants Binary(Add, Constant, %inner) Yes The output of one fusion is itself a Binary(Add, Constant, V, %dst) — exactly the shape the next outer match looks for as a producer.

For RecognizeIndexedStore and RecognizeIndexedLoad — the passes that collapse ZeroExtend + Binary(Add, Constant) + Store/Load into IndexedStore / IndexedLoad — the output is a new instruction kind that the pattern doesn't match, so chaining isn't possible either.

The summary: instructions_view matters exactly when a pass can produce output that it can also consume. ReassocConstants is the only current subclass in that category. For the others, the mechanism is a no-cost invariant: it's always correct, sometimes useful.

What it taught

1. A pattern-matching framework's state is more than its def-index. The def-index maps names to instruction indices. That's static — it doesn't change during the pass because indices don't change. What DOES change is the instruction at each index, once a rewrite fires. A framework that maintains the def-index but not the instruction content under rewrites has a stale-read problem for any lookup that fires after a write. instructions_view is the minimal patch: one extra list, updated alongside rewrites, pointed at by env.instructions.

2. The outer fixed-point loop is not free. Each TAC fixed-point iteration runs twelve passes over the whole function. For a three-pair constant chain with the naive design, the second fusion takes an extra outer iteration — twelve passes, then another twelve, before the result is stable. For deeply nested constant arithmetic (pointer + table offset + column index + ...) the cost compounds. The instructions_view fix collapses all pairs in one pass of one outer iteration.

3. Eager drops are necessary for post-fixedpoint passes. Inside the fixed-point loop, leaving dead defs is fine — DSE is one of the twelve passes, and it runs on every iteration until convergence. Outside the loop — in PostFixedpointPass and PostDestructionPass — there is no following DSE. A pass that drops its inner defs lazily, expecting cleanup later, will instead see those defs survive into tac_to_asm. Rewrite.drop_defs gives post-fixedpoint passes the ability to atomically remove what they've consumed, without depending on a later sweep that won't come.

4. The general principle is composability with self. A rewrite system is sound if each rewrite in isolation produces a correct result. But a rewrite system where the rules compose — where a rule's output can be the input to the same rule — needs the intermediate state to be visible to later rule applications in the same pass. LLVM's instruction combiner handles this by working backward (from the current instruction toward its defs) and re-adding instructions to a worklist when their operands change. DefUsePass handles it by keeping a mutable view of the instruction stream that reflects in-progress rewrites. Both approaches share the same underlying insight: a pattern matcher that can only see the original IR is a pattern matcher that can only peel one layer per pass.

The implementation is five lines of additional mechanism in DefUsePass.run: one list creation, two assignments inside the rewrite loop, and the env.instructions field pointer. The correctness argument is correspondingly local: any subsequent env.def_of reads the list at its current state, which includes all rewrites committed so far. That's all it takes to make chained fusions work.
