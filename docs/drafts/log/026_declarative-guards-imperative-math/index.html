Compiler log · #026

Declarative guards, imperative math

The wish was for a table-driven optimizer where each peephole is data, not code. Most of that wish runs into a wall — but the wall is in a precise, nameable place, and on the near side of it there's a real win.

Project c6502 Subject table-based peephole framework New RuleSet / Rule / RuleEnv Files passes/optimization/framework/rules.py

The hope

c6502's TAC optimizer is a fixed-point loop over a couple dozen peephole passes. Each one had grown into the same shape: a class with a pattern, a prepare hook for whole-function analysis, and a rewrite method full of bespoke logic. The pattern-matching had already been factored into an LLVM-style combinator DSL — m_Binary, m_Unary, m_OneOf — but the rewrite bodies were still hand-written per pass.

The wish was the obvious next step: make the rewrite half table-based too. A pass becomes data — a list of (pattern, guard, replacement) rows — and a generic engine applies them. Less unique code per pass; ideally, fewer passes. The model is a term-rewriting system: LHS ⇒ RHS with side conditions, declared rather than coded.

Before building anything, I read the actual rewrite bodies. That reading is the whole story, because it draws a sharp line between the part of the wish that's achievable and the part that's a trap.

Half of it was already declarative

The patterns were the easy half, and they were done. Here's the canonical shape shared by a whole family of folds — a boolean-producing instruction immediately consumed by a conditional jump:

[ m_Unary(op=LogicalNot, src=m_Any(capture='src'), dst=m_Var(capture='t')),
  m_OneOf(
    m_JumpIfTrue(condition=m_Specific('t'),  capture='jmp'),
    m_JumpIfFalse(condition=m_Specific('t'), capture='jmp'),
  ) ]

m_Specific('t') is a back-reference: the jump's condition must be the very same Var the producer wrote. That's already a declarative description of "a single-use boolean feeding the next branch." Nothing imperative about it. The question was never the pattern — it was what happens after a match.

Three kinds of rewrite

Sorting the folds by what their rewrite actually does, three categories fall out, and they behave very differently under "turn this into a table."

Category 1 — structural

The replacement is the captured fields, reassembled. The LogicalNot-into-jump fold is the poster child: !x jumped-on is x jumped-on with the opposite sense. The entire transform:

jmp = m.bindings['jmp']
src = m.bindings['src']
cls = JumpIfFalse if isinstance(jmp, JumpIfTrue) else JumpIfTrue
return [cls(condition=src, target=jmp.target)]

No value is computed. This is a template — pick a class, reuse two fields. Category 1 genuinely collapses to near-zero unique code.

Category 2 — computational

The replacement requires arithmetic. Strength reduction turns Multiply(x, 2^k) into a left shift — but it has to compute k = log2(const), and Modulo(x, 2^k) into BitwiseAnd(x, 2^k - 1), building a mask constant of the right type variant. Constant reassociation folds C1 + C2 with width-correct wraparound at the operand's declared width.

You can put these in a table — but the table cell has to hold a Python callable that does exactly that math. You've moved the code into a build= field, not eliminated it.

Category 3 — multi-step

The comparison-fold and the addressing-mode recognizers walk backward through the SSA def-chain, query the symbol table for operand widths, range-check constants, and drop several dead defs atomically. The comparison fold's narrowing path traces a value back through a ZeroExtend, checks the source is a 1-byte unsigned type, and only then rewrites (uint8_t)i < 105 into a 3-instruction LDA / CMP / BCS. That's control flow, not a template.

Where the table stops

The trap

Forcing categories 2 and 3 into a value-level meta-DSL produces something harder to read than the if isinstance(op, Multiply) ladder it replaced. The arithmetic is the pass. A meta-language for "compute log2, build a constant of the matching variant, wrap modulo the width" is just a worse Python.

And there's a fourth bucket that never enters the conversation at all: the roughly nine CFG-shaped passes — SSA construction and destruction, copy propagation, dead-store and dead-loop elimination, unreachable-code elimination. Those are whole-function dataflow. No per-site pattern applies. They stay hand-written, and should.

So the table tops out well short of "the whole optimizer." The honest target is not everything is a table. It's: declarative pattern, declarative guards, imperative math.

The part that does factor: guards

Here's the thing the category taxonomy reveals. The recurring content across these passes isn't in the builds — those are either trivial (category 1) or irreducibly unique (2 and 3). It's in the guards. The same soundness checks appear over and over:

  • single-use — the producer's dst is read exactly once, so folding its sole consumer leaves it dead. Six passes hand-rolled this.
  • SSA-renamed — gate a def-chain walk on the name having a single def.
  • byte-typed — the operand's C type is one byte. Copy-pasted across all three addressing-mode recognizers.
  • have-symbols — skip the pass when no symbol table is present.

These are exactly what wants to be declarative. So the framework that pays off isn't a replacement-template engine — it's a guard library plus a thin shell that owns the recurring scaffolding:

LNOT_RULE = Rule(
    name="fold_lnot_jump",
    pattern=producer_then_jump(
        m_Unary(op=tac_ast.LogicalNot,
                src=m_Any(capture='src'), dst=m_Var(capture='not_dst')),
        on='not_dst',
    ),
    where=[single_use('not_dst')],     # declarative guard combinator
    build=_build_lnot_jump,            # (m, env, ctx) -> list | None
)

The where=[...] list is the declarative part. The build is a callable — a one-liner for category 1, a real function for 2 and 3. Guards declarative, math imperative, on purpose.

RuleSet

The shell is RuleSet: a fixed-point pass driven by a list of Rules. It owns three things every fold used to repeat by hand.

The window scan. Slide over the instruction list; at each position try each rule's pattern, then its guards, then its build. First rule that fires wins; advance past the window it consumed.

The shared analyses. A RuleEnv, built once per run, carries the use-count map and a name-to-defining-instruction index, with def_of(var) and is_single_use(var) helpers. The build reads these instead of recomputing its own — and they're built on the codebase's canonical operand-walkers, so they can't drift out of sync with the IR the way the old per-pass copies did.

The guard evaluation. Guards are small closures over a capture name:

def single_use(capture):
    return lambda m, env, ctx: env.is_single_use(m.bindings.get(capture))

What a fold used to spell as a class with window_size, pattern, a prepare that built a three-tuple of analyses, and a rewrite that opened with a hand-written single-use check — is now a Rule value plus, for category 1, a six-line build.

Three passes, one sweep

The payoff that best honors "fewer passes" is that disjoint rules compose. Three folds in the pipeline matched the identical window — a producer feeding a single-use jump — differing only in the producer's opcode:

FoldProducerEmits
fold_lnot_jumpUnary(LogicalNot)sense-flipped JumpIf
fold_cmp_zero_jumpBinary(==, <, …)JumpIfCmp / bare JumpIf
fold_narrow_and_jumpBinary(BitwiseAnd)JumpIfMasked

They had been three separate passes, each sweeping the whole function in turn. As three Rules in one RuleSet, they apply in a single sweep — whichever rule matches at each position.

Why the merge is sound

The producer opcodes are disjoint, so at most one rule can match any window. And every rule emits a jump, never a producer — so no rule can rewrite another's output. The merged sweep therefore reaches the same fixed point as three separate sweeps. The full test suite, including the byte-exact assembly golden files, came out identical.

Each module still exports its own rule and keeps its standalone entry point — as a one-rule RuleSet — so the unit tests that drive each fold in isolation are untouched. The pipeline is the only place the three combine.

The honest scorecard

Raw line count came out roughly flat. About 240 lines of per-pass boilerplate — class scaffolding, prepare hooks, duplicated single-use gates — became one reusable rules.py. That's not a shrink; it's a relocation.

But line count was never the goal. What changed is structural:

  • The recurring guards are named once and reused, instead of re-spelled at the top of every rewrite.
  • The category-1 fold dropped to a declarative rule plus a six-line build — exactly the table-based form the wish asked for.
  • Three pipeline passes became one.
  • The next pass that wants this shape inherits the whole apparatus for free.

And the categories-2-and-3 folds shed their scaffolding without anyone pretending their arithmetic is data. They kept their real builds. That restraint is the point: the win came from knowing where the table stops. A peephole framework earns its keep on the structural rewrites and the shared guards; it loses by an over-reach into computational replacement that reads worse than the code it abstracts.

The pattern was always declarative. The guards wanted to be. The math never did.
