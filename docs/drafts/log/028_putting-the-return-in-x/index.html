Compiler log · #028

Putting the return in X

Swapping __attribute__((reg(...))) for the C register keyword meant a small ABI change: a two-byte integer now comes back in A and X instead of zero-page. That one change put a live value in X across a call boundary for the first time — and woke up five latent peephole bugs that had been asleep precisely because nothing ever did that.

A two-byte return in two registers

c6502 used to pin parameters and return values to specific 6502 registers with a GCC-style extension: __attribute__((reg("A"))). The new spelling is the standard C register keyword, with positional assignment — the first register arg-byte goes in A, the second in X. A local pins to Y. And the return value goes the same way: a non-pointer value of two bytes or fewer comes back low byte in A, high byte in X. Pointers and wider types still ride a zero-page exchange block called HARGS.

That last clause is the whole story. Under the old convention, a two-byte int was returned through HARGS — a pair of zero-page cells. The new convention returns it in registers. So this:

unsigned int g(register unsigned int a) { return a; }

compiles, under --optimize, to exactly one instruction:

g:
   RTS

The argument arrives low-in-A, high-in-X; the identity return wants it low-in-A, high-in-X; there is nothing to do. That is the kind of result that tells you the convention is right.

It is also the kind of result that should have made me nervous. For the entire prior life of the compiler, X was scratch — an index register, a loop counter, a place to stash the low byte of a frame pointer mid-teardown. Nothing ever expected a meaningful value to survive in X across a JSR or through a function epilogue. Every register- and flag-tracking peephole had been written, and tested, against a world where that never happened. The new ABI made it happen everywhere. Five bugs fell out, each one a place where an assumption that had always been true quietly stopped being true.

The epilogue that ate the return

The first one showed up in fib. Recursive, so it can't use the zero-page calling convention; it gets a real soft-stack frame, which means a real epilogue that tears the frame down before RTS. A recursive int-returning function now leaves its result in A and X — and the teardown clobbers both. A was already handled: the epilogue pushed it, did its 16-bit pointer arithmetic, and pulled it back. X was new.

So I taught the teardown to park both bytes on the hardware stack and pull them back just before RTS. There's no PHX on the NMOS 6502, so the high byte routes through A:

   PHA            # push low (A)
   TXA            # A := high
   PHA            # push high
   # ... SSP/FP teardown clobbers A and X ...
   PLA            # A := high
   TAX            # X := high
   PLA            # A := low
   RTS            # A=low, X=high — convention restored

Wrote it, ran fib(6), got 0. Expected 8.

The teardown isn't the only thing in an epilogue. Before it runs, the function restores its callee-saved zero-page bytes — and that uses A as scratch too. My save/restore bracket sat inside the callee-save restore, so by the time I pushed A it no longer held the return value; it held whatever the last restore had loaded. The fix was embarrassingly small — hoist the push above the restore — but the bug had been latent the whole time. A one-byte return from a callee-saved function would have hit it years ago, except no recursive function in the corpus returned a char. Putting int returns in A/X was the first thing to walk that path.

The carry that no longer threaded

Next was an arithmetic miscompile in a tiny program: (0==0 && ...) + 1, expected 1, optimized build returned 257. The high byte was wrong by one.

The culprit was the multi-byte INC peephole. A two-byte x + 1 lowers to an add-with-carry chain: CLC; ADC #1 on the low byte, ADC #0 on the high byte, the carry threading between them. When both bytes are an in-place memory read-modify-write, the peephole collapses the whole chain to INC instructions — much shorter. But INC doesn't touch the carry flag, and that's fine as long as the whole chain is folded: nothing downstream reads the carry the chain used to produce.

The new return path broke that invariant. The high byte's result now flowed into X (the return register) instead of back to memory, so it wasn't an in-place RMW and didn't fold. The peephole folded the low byte to a carry-less INC anyway — and left the high byte's ADC #0 sitting there, reading a carry that INC never set:

   INC   __local_x       # low += 1 — but sets no carry
   LDA   #$00
   ADC   #$00            # high := 0 + 0 + STALE carry
   TAX                   # return high byte

The fix: before folding, scan past the chain for a carry-consuming ADC continuation, and refuse the whole fold if one is there. The low byte stays an honest SEC; SBC—style chain, the carry threads, the answer is 1.

The dead store that clobbered A

Then a caller-side bug: foo() + bar, where foo returns int. The capture is clean — store A to the result's low slot, X to its high slot — and the addition that follows is correct in the IR. But the optimized output added bar to the wrong byte. Both halves of the sum were reading the high byte.

This one took a per-pass dump to localize. The pre-peephole IR was correct. A rematerialization pass corrupted it. Its job: when a value staged into a __local slot is never read again, the slot store is dead, so collapse Mov(src, slot) to Mov(src, A) — keep the value in A, drop the store, let a later pass clean up the load. Reasonable, for a LDA src; STA slot staging pair where A was going to be clobbered anyway.

But the dead store here was STX slot — storing the return's high byte to a slot that turned out unused. Collapsing STX slot to Mov(Reg(X), Reg(A)) is TXA, which clobbers A — and A held the live low byte the next instruction needed:

   STA   __local_lo      # A = foo() low — LIVE
   TXA                   # was STX __local_hi (dead). Clobbers A!
   CLC
   ADC   bar             # adds bar to foo()'s HIGH byte

A register-source dead store has no flag or A side effect at all — it's pure dead code. The fix is to drop it, not transmute it into an A-write. The memory-source case (a real LDA) keeps its old behavior; only STX/STY changed.

The flag scan that forgot LDA

The last one I could fully fix lived in the DEC peephole, and it's my favorite because the wrong assumption is one sentence long.

DEC folds LDA M; SEC; SBC #1; STA M into a single DEC M. SBC sets the carry and overflow flags; DEC sets only N and Z. So the fold is unsound if anything downstream branches on C or V — and the peephole had a guard that scanned forward for exactly that. The guard treated LDA/STA as "resets the flags, stop scanning, safe to fold."

That's the bug. On the 6502, LDA and STA set N and Z but do not touch the carry. The carry from a prior SBC threads straight through them. So this:

   # ... SBC #1 (folded to DEC) ...
   STA   slot            # carry survives
   LDA   other           # carry survives
   BCC   target          # reads the SBC's carry — gone after DEC

folds SBC to DEC and then a BCC three instructions later reads a carry that no longer exists. The old guard stopped at the first STA and declared victory. The new register ABI shifted enough code around that this shape started appearing.

The honest version is a small control-flow walk: scan forward over the genuinely carry-transparent opcodes (loads, stores, transfers, logicals, INC/DEC, push/pop, BIT), follow both arms of any non-carry branch, stop safe at anything that redefines C — and report unsafe the moment a BCC/BCS/BVC/BVS is reachable first. It's more code than the original line-by-line scan, but it's the difference between "looks done" and "is correct."

The one I pinned

There was a sixth. In one subsystem, a uint16_t-returning helper is called twice per loop iteration, and the high byte — now living in X — gets clobbered before its != 0 test. Disabling any single peephole doesn't fix it; only disabling the DEC fold does, and the DEC fold is correct now. So it isn't a single-pass soundness bug — it's a regalloc/scheduling interaction that the DEC fold merely perturbs into existence, by changing the instruction stream enough to make the allocator reuse X while the high byte is still live.

That's a different and harder class of fix than the other five, and chasing it further would have held up a working feature for a corner case. I pinned the two optimized-path assertions as expected failures, with the root cause written down, and left the unoptimized correctness test live. Knowing which kind of bug you're looking at — a local soundness slip versus a global allocation interaction — is most of the decision about whether to fix it now or bank it.

What it taught

The feature itself was the easy part: a keyword, a positional rule, a type-driven return. The work was the five bugs, and four of them had been dormant for the same reason. Every one was a peephole that had quietly encoded "X is never a live value across this boundary" or "a register store always has a side effect worth keeping" or "a load resets the flags" — assumptions that were true of the code the old ABI produced, and stopped being true the moment a return value moved into X.

  • A calling-convention change is a fuzzer for your soundness assumptions. It doesn't add new opcodes; it changes where live values are, and every analysis that hard-coded "nothing lives here" gets exercised at once. If you're about to move data into a register that scratch passes have always been free to clobber, expect to find every place that assumed they could.
  • "Sound enough for the corpus" is a real category, and it expires. The INC and DEC carry guards, the dead-store collapse, the epilogue bracket — all were correct for every program the compiler had ever seen. None were correct in general. The new ABI didn't break them; it stopped hiding them.
  • Bisect before you trace. I lost real time hand-simulating register-mirror state across fixedpoint iterations. The fast path was mechanical: monkeypatch each pass to identity, re-run, watch which removal makes the miscompile vanish; if no single one does, dump the function after every pass and read for the corrupting transition. (And do it through the codegen entry point, not the simulator harness — they run different pipelines.)
  • Classify the residual before you commit to it. Five of the six were local soundness slips with small, surgical fixes. The sixth was a global allocation interaction — a different animal. Naming which kind you're staring at is most of the decision to fix-now versus pin-and-bank.
You don't change a calling convention. You change where the values are — and then you find out which of your assumptions were only ever true by luck.
