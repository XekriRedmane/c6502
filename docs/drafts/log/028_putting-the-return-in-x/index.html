Compiler log · #028

Putting the return in X

Replacing __attribute__((reg(...))) with the C register keyword came with a small ABI change: a two-byte integer now returns in A and X instead of zero-page. That put a live value in the X register across call boundaries, which the compiler had never done before — and surfaced five peephole bugs whose soundness checks had assumed it never would. This post walks through each one.

A two-byte return in two registers

c6502 used to pin parameters and return values to specific 6502 registers with a GCC-style extension: __attribute__((reg("A"))). The new spelling is the standard C register keyword, with positional assignment — the first register arg-byte goes in A, the second in X. A local pins to Y. And the return value goes the same way: a non-pointer value of two bytes or fewer comes back low byte in A, high byte in X. Pointers and wider types still ride a zero-page exchange block called HARGS.

That last clause is what the bugs hinge on. Under the old convention, a two-byte int was returned through HARGS — a pair of zero-page cells. The new convention returns it in registers. So this:

unsigned int g(register unsigned int a) { return a; }

compiles, under --optimize, to exactly one instruction:

g:
   RTS

The argument arrives low-in-A, high-in-X; the identity return wants it low-in-A, high-in-X; there is nothing to do.

The relevant detail for the rest of this post: before this change, X was only ever scratch — an index register, a loop counter, a place to stash the low byte of a frame pointer mid-teardown. No value was expected to survive in X across a JSR or through a function epilogue. Several register- and flag-tracking peepholes encoded that as an assumption — usually implicitly, in what they did or didn't check. Returning two-byte values in X violates it, and five bugs followed.

The epilogue that ate the return

The first one showed up in fib. Recursive, so it can't use the zero-page calling convention; it gets a real soft-stack frame, which means a real epilogue that tears the frame down before RTS. A recursive int-returning function now leaves its result in A and X — and the teardown clobbers both. A was already handled: the epilogue pushed it, did its 16-bit pointer arithmetic, and pulled it back. X was new.

So I taught the teardown to park both bytes on the hardware stack and pull them back just before RTS. There's no PHX on the NMOS 6502, so the high byte routes through A:

   PHA            # push low (A)
   TXA            # A := high
   PHA            # push high
   # ... SSP/FP teardown clobbers A and X ...
   PLA            # A := high
   TAX            # X := high
   PLA            # A := low
   RTS            # A=low, X=high — convention restored

Wrote it, ran fib(6), got 0. Expected 8.

The teardown isn't the only thing in an epilogue. Before it runs, the function restores its callee-saved zero-page bytes — and that uses A as scratch too. My save/restore bracket sat inside the callee-save restore, so by the time I pushed A it no longer held the return value; it held whatever the last restore had loaded. The fix is to hoist the push above the restore. This bug was already present: a one-byte return from a callee-saved function would have hit it, but no recursive function in the test corpus returned a char, so the path was never taken until int returns moved into A/X.

The carry that no longer threaded

Next was an arithmetic miscompile in a tiny program: (0==0 && ...) + 1, expected 1, optimized build returned 257. The high byte was wrong by one.

The culprit was the multi-byte INC peephole. A two-byte x + 1 lowers to an add-with-carry chain: CLC; ADC #1 on the low byte, ADC #0 on the high byte, the carry threading between them. When both bytes are an in-place memory read-modify-write, the peephole collapses the whole chain to INC instructions — much shorter. But INC doesn't touch the carry flag, and that's fine as long as the whole chain is folded: nothing downstream reads the carry the chain used to produce.

The new return path broke that invariant. The high byte's result now flowed into X (the return register) instead of back to memory, so it wasn't an in-place RMW and didn't fold. The peephole folded the low byte to a carry-less INC anyway — and left the high byte's ADC #0 sitting there, reading a carry that INC never set:

   INC   __local_x       # low += 1 — but sets no carry
   LDA   #$00
   ADC   #$00            # high := 0 + 0 + STALE carry
   TAX                   # return high byte

The fix: before folding, scan past the chain for a carry-consuming ADC continuation, and refuse the whole fold if one is there. The low byte stays an honest SEC; SBC—style chain, the carry threads, the answer is 1.

The dead store that clobbered A

Then a caller-side bug: foo() + bar, where foo returns int. The capture is clean — store A to the result's low slot, X to its high slot — and the addition that follows is correct in the IR. But the optimized output added bar to the wrong byte. Both halves of the sum were reading the high byte.

This one took a per-pass dump to localize. The pre-peephole IR was correct. A rematerialization pass corrupted it. Its job: when a value staged into a __local slot is never read again, the slot store is dead, so collapse Mov(src, slot) to Mov(src, A) — keep the value in A, drop the store, let a later pass clean up the load. Reasonable, for a LDA src; STA slot staging pair where A was going to be clobbered anyway.

But the dead store here was STX slot — storing the return's high byte to a slot that turned out unused. Collapsing STX slot to Mov(Reg(X), Reg(A)) is TXA, which clobbers A — and A held the live low byte the next instruction needed:

   STA   __local_lo      # A = foo() low — LIVE
   TXA                   # was STX __local_hi (dead). Clobbers A!
   CLC
   ADC   bar             # adds bar to foo()'s HIGH byte

A register-source dead store has no flag or A side effect at all — it's pure dead code. The fix is to drop it, not transmute it into an A-write. The memory-source case (a real LDA) keeps its old behavior; only STX/STY changed.

The flag scan that forgot LDA

The last single-pass bug lived in the DEC peephole, and the wrong assumption is one sentence long.

DEC folds LDA M; SEC; SBC #1; STA M into a single DEC M. SBC sets the carry and overflow flags; DEC sets only N and Z. So the fold is unsound if anything downstream branches on C or V — and the peephole had a guard that scanned forward for exactly that. The guard treated LDA/STA as "resets the flags, stop scanning, safe to fold."

That's the bug. On the 6502, LDA and STA set N and Z but do not touch the carry. The carry from a prior SBC threads straight through them. So this:

   # ... SBC #1 (folded to DEC) ...
   STA   slot            # carry survives
   LDA   other           # carry survives
   BCC   target          # reads the SBC's carry — gone after DEC

folds SBC to DEC, and then a BCC three instructions later reads a carry that no longer exists. The old guard stopped scanning at the first STA and reported the fold safe. The new register ABI shifted enough code around that this shape started appearing.

The honest version is a small control-flow walk: scan forward over the genuinely carry-transparent opcodes (loads, stores, transfers, logicals, INC/DEC, push/pop, BIT), follow both arms of any non-carry branch, stop safe at anything that redefines C — and report unsafe the moment a BCC/BCS/BVC/BVS is reachable first. More code than the original line-by-line scan, but it's the actual condition for the fold being sound.

The sixth, in a register allocator

There was a sixth. In one subsystem, a uint16_t-returning helper is called twice per loop iteration; the high byte — now in X — gets clobbered before its != 0 test. Disabling any single peephole doesn't fix it; only disabling the DEC fold does, and the DEC fold is correct now. So it isn't a single-pass soundness bug. It's a register-allocation interaction the DEC fold only perturbs into existence: the changed instruction stream lets the loop-counter-to-X promotion fire, and that promotion reuses X while the return high byte is still live.

That's a different class of fix from the other five — it's in a promotion pass, not a flag/register tracker — and it gets its own writeup in #029, along with the register-param + register-local frame bug that turned out to share a root cause with it.

The five fixes

All five were one-pass soundness slips with small, local fixes. Each had been correct for every program the old ABI produced and only became reachable once a return value lived in X.

The two debugging moves that paid off: bisect by patching each pass to the identity function and recompiling to see which removal makes the miscompile vanish (and do it through the codegen entry point — the simulator harness runs a slightly different pipeline); and when no single pass is responsible, dump the function after every pass in one fixedpoint iteration and read for the transition that corrupts it.
