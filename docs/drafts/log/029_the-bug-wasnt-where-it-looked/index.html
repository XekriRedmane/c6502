Compiler log · #029

The bug wasn’t where it looked

The register-ABI change (#028) left two bugs I pinned rather than fixed. Coming back to them, both turned out to present several passes away from their actual cause — one in a register allocator that didn’t know the calling convention had changed under it, one in a single is not None three passes upstream that had been silently deleting code for far longer than the new feature.

Two symptoms, two scenes

Two loose ends came out of moving 2-byte integer returns into the A/X register pair. Both were real miscompiles I'd written down and deferred, because each one's symptom sat somewhere that looked nothing like a calling-convention problem.

The first lived in a game subsystem's update loop. A helper returns a uint16_t screen coordinate; under the new ABI that comes back in A and X. The loop calls it twice per iteration, tests the high byte for zero, uses the low byte as an array index. Optimized, it computed garbage. Disabling any one of three different optimization passes made it go away — which is the signature of an interaction, not a single broken pass.

The second was simpler to trigger and stranger to look at. A leaf function with a register parameter and a register local — each fine on its own — grew a soft-stack frame when combined, and the frame's prologue clobbered the incoming argument before the function could read it:

sum_n:
   # ... prologue does its 16-bit SSP/FP math, trashing A ...
   STA   __zpabi_sum_n__n      # save the arg — but A is already gone

That second one looks like an ordering bug: the entry stub that saves the register argument runs after the prologue, so move the stub earlier. That fix would work — but it leaves open the better question of why there's a prologue here at all.

The promoter that didn’t know

The loop bug first. Bisecting — patch each candidate pass to the identity function, recompile, see which removal makes the miscompile vanish — pointed at three optimizations that all promote a value into the X register: a loop-counter-to-X pass, a dual-index promoter, an increment-compare fusion. Disabling any one fixed it. They were chaining.

The shared mechanism was the loop-counter promotion. It takes a counter that lives in a zero-page cell and keeps it in X across the whole loop body — the classic hand-written 6502 idiom. The complication is calls: a JSR clobbers X, so the pass brackets every call in the loop with a save and a restore:

   STX   counter_slot      # save X before the call
   JSR   helper
   LDX   counter_slot      # restore X after the call

That bracket encodes an assumption: the callee delivers nothing in X. X is the counter's home; the call can only damage it, so we save and restore around the damage. True for the entire prior life of the compiler — and false the day a 2-byte return started handing its high byte back in X. Now the instruction right after the JSR isn't free real estate; it's where the caller captures the return:

   STX   counter_slot      # save counter
   JSR   helper            # returns high byte in X
   LDX   counter_slot      # restore — clobbers the return high byte!
   STX   result_hi         # captures the counter, not the return

Two live values, one register. The counter and the return high byte both want X across the same instruction, and the promoter happily wrote code that pretends only one of them exists. The other passes in the chain were just shuffling enough around to make this promotion fire.

A guard that follows the branches

The fix is to teach the promoter the thing it didn't know: refuse to promote across a call whose return value is live in X. The tell is right there in the instruction stream — does anything read X after the JSR before X is overwritten? A return capture (STX result_hi, or TXA) reads X. The ordinary counter case instead reloads X with LDX counter_slot — a pure write — before any use.

The subtlety is that the counter's reload often happens at the top of the loop, reached across the back-edge, not on the straight line after the call. A linear scan that stops at the first branch over-rejects and kills the optimization on every normal loop. So the check follows control flow — both arms of a conditional branch, jump targets, the loop back-edge — and resolves each path independently:

def _call_returns_live_x(instrs, call_idx):
    # walk forward from the call, following branches
    for each reachable instr:
        if instr reads X:              return True   # live return in X — refuse
        if instr is a pure write to X: prune path    # LDX/TAX — counter reload
        if instr is another Call:      prune path    # clobbers X anyway
        if instr is Ret with save_x:   return True    # epilogue returns X
    return False

For the buggy loop the first instruction after the call reads X — refuse, leave the counter in its zero-page cell, done. For an honest counter loop the only thing that touches X is the reload at the loop top, reached around the branch — a pure write, every path prunes clean, the promotion proceeds exactly as before. The existing loop-counter tests stayed green, which is how you know the guard is narrow and not a sledgehammer.

A prologue eats an argument

Now the frame bug. The instinct is strong here: the entry stub that saves the register argument is emitted as the first body instruction; the prologue gets prepended later; the prologue runs first and trashes A. Reorder them. It would even work.

So: why is there a prologue at all? sum_n is a leaf, non-recursive, address never taken — exactly the shape that's supposed to get a private zero-page slice for its locals and emit as bare body + RTS, with no frame and no prologue to reorder. Something forced the frame, and that's what to chase.

I handed the trace to a sub-agent: figure out why sum_n isn't bare-exit. The answer came back with a value name I didn't expect — @1.acc, the register char acc = 0 local, sitting on the frame as a read with no reaching definition. The function got its private pool correctly. The Y-pinned acc got its register correctly. But there was a second, ghost acc — a use of a value that was never written — and that ghost is what landed on the frame and dragged the prologue in with it.

One is not None too many

A read with no write means the write was dropped. In the AST-to-TAC lowering, block-scope declarations are handled like this:

case VarDecl(var_decl=vd):
    if vd.storage_class is not None:
        return                 # static / extern: defined elsewhere, no code here
    ... emit the initializer ...

The intent: a block-scope static int x = 1; or extern int y; has static storage duration — its definition lives in the program's data section, and the declaration emits no code at its source location. The storage_class is not None test was the shorthand for "has static storage duration."

It used to be exact. There were only two storage classes that reached this point: static and extern. Adding the register keyword added a third — and a register local is automatic storage. Its initializer absolutely must run. But it carries a storage_class too, so is not None swept it into the static bucket and the entire acc = 0 was dropped on the floor.

The fix is to say what was always meant:

    if isinstance(vd.storage_class, (Static, Extern)):
        return

This is broader than the reported symptom. It has nothing to do with the frame, or the combination of param and local: every register T x = init; was silently dropping its initializer. It hadn't surfaced before because when the dropped initializer didn't force a frame, the uninitialized value was usually overwritten before being read, or coalesced into a register that was about to be loaded anyway. sum_n was just the first arrangement where the dropped store became observable.

The un-versioned name

The detail that pointed upstream is in the name itself. In the SSA form, every name gets a per-definition version suffix — @1.acc becomes @1.acc.1.b0.v2 and so on. SSA construction only versions names that have a reaching definition; a use with no def stays bare: @1.acc, no suffix. A bare name is invisible to register coloring — it's in neither the color map nor the hardware-register-pin map — so it falls straight through to the frame.

So an un-versioned Pseudo on the frame is a reliable tell: not a bad allocator choice, but a value that was never defined, with the real bug upstream in whatever should have defined it. From there the confirmation is a one-line diff — dump the TAC (compile.py - --tac) for the working variant (plain char acc = 0) next to the broken one (register char acc = 0) and find the missing instruction. The working one has a Copy(0 → acc); the broken one has nothing.

Two things worth repeating from the chase. The pass you can disable to make a miscompile disappear is a lead, not the culprit: loop_counter_to_x wasn't wrong on its own — it was correct against an assumption (nothing returns in X) the ABI change had invalidated. And the second fix is one line in a place three passes away from the symptom; the obvious local patch (reorder the entry stub and the prologue) would have made sum_n compile correctly while leaving every other register T x = init; silently broken.
